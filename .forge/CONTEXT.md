# BibleMap — 도메인 용어집

## 구절 근거 원칙 (verse-grounded principle)

이 사이트가 사용자에게 보여주는 모든 분석·서술 정보는 **성경 구절을 근거로 삼는 것이 제1규칙**이다. 근거 구절 없는 진술을 화면에 두지 않으며, 데이터를 만들거나(저작·큐레이션) 지우는(중복 제거 등) 작업은 결과물이 구절 근거를 잃지 않는지를 기준으로 검증한다 — 인물 소개·성품이 진술마다 근거 절을 다는 것, 사건이 근거 구절(📖)을 갖는 것이 모두 이 원칙의 사례.
_Avoid_: "참고 구절"(장식적 인용이라는 뉘앙스 — 구절은 장식이 아니라 근거다)

## Theographic ID

Theographic Bible Metadata 레포에서 사용하는 Airtable 레코드 ID. `rec` 접두사로 시작하는 14자 문자열 (예: `recv0dAY2ULzJ687g`). 모든 엔티티(Person, Place, Event, PeopleGroup)의 안정 키. 영문명은 동명이인이 존재하므로 조인·참조 기준으로 사용하지 않는다. Neo4j 노드의 `theographic_id` 속성으로 저장된다.

## publish 레코드

Theographic 데이터에서 `fields.status == "publish"`인 레코드. 데이터가 검수 완료된 상태. `status == "wip"` 레코드는 미완성이므로 BibleMap 적재에서 제외한다.

**예외 — 가족 폐포 wip 인물 (ADR-0021)**: Person에 한해, publish 인물에서 가족 필드(father/mother/children/partners/siblings)로 도달 가능한 wip 레코드는 노드로 적재한다. [[가계도-family-tree]]의 혈통 완전성을 위해서다(다윗의 자녀 21명 중 publish는 솔로몬뿐). 단 3중 격리를 지킨다 — `status: "wip"` 속성 마킹, **가족 간선만** 적재(사건 참여·그룹 등 나머지 간선은 publish 전용), `/search` 결과에서 제외. 폐포 밖 wip(고아 섬)과 Person 외 엔티티는 여전히 전면 제외다.

**엔티티별 status 필드 유무**: Person·Place는 `status` 필드가 있다. Event·PeopleGroup은 `status` 필드가 없으므로 "전체 포함"으로 처리한다(`fields.get("status", "publish") == "publish"` 패턴). Verse·Book·Chapter 등 추가 엔티티를 적재할 때는 `status` 필드 유무를 먼저 확인해야 한다.

## Period

별도의 엔티티 타입 없음. 성경의 시대(족장 시대, 왕국 시대 등)는 `Event` 노드의 `PART_OF` 관계로 표현한다. 상위 Event가 하위 Event들을 포함하는 계층 구조.

## Book

성경 각권을 나타내는 Neo4j 노드 (label: `Book`). Theographic `books.json`에서 적재. 주요 속성: `theographic_id, name, nameKo, testament(구약/신약), genre, authorKo, startYear, endYear, chapterCount`. 추가 속성(LLM 생성 후 주입): `background`(시대적 배경 텍스트), `themes`(성경 주제 배열), `keyVerse`(대표 구절 참조). Book → Event 관계는 `CONTAINS_BOOK`.

**CONTAINS_BOOK 관계 생성 방법**: `Book.verses ∩ Event.verses` 교집합. Theographic events에 scripture 직접 참조 필드가 없으므로, Book이 포함하는 구절 배열과 Event의 구절 배열의 교집합이 비어있지 않으면 `CONTAINS_BOOK` 관계를 생성한다 (`load_books.py`). 파이프라인 재실행·관계 수정 시 이 방식을 유지해야 한다.

**의미**: `(Book)-[:CONTAINS_BOOK]->(Event)`는 "그 책이 그 사건을 기록한다" = **사건의 성경적 근거**를 뜻한다. 한 사건을 여러 권이 기록할 수 있다(예: 공관복음 평행 기사 → 마/막/눅).

**발생(primary) vs 회고 인용 (ADR-0012)**: 한 사건의 참조가 여러 책에 걸칠 때, **첫 참조(authored=`books[0]`, theographic=`verses[0]`의 책)가 발생 위치**이고 나머지는 **다른 책의 회고 인용**이다(예: 아브라함 부름은 창세기에서 *발생*하고 사도행전 스데반 설교가 *인용*). 관계에 `primary` 불리언으로 구분하며, Book의 "주요 사건(topEvents)·주요 인물(topPersons)·지도 장소"는 `primary` 관계만 집계한다(회고 인용이 그 책 파생 뷰를 오염시키지 않도록). 반대로 사건 행의 📖 근거 칩(사건→기록 책)은 인용도 정당한 근거라 primary로 거르지 않는다. 한계: 서신서가 신학적으로 회고하는 사건(히 11장 믿음의 선진 등)은 verses[0]가 그 서신이라 서신을 발생으로 오판정할 수 있다(서신서는 CONTAINS_BOOK으로 연대·발생 판정 불가 — 실 저작일은 [[저작-사건-authored-event]]). 사건의 날짜가 없는 책(서신서·시편·잠언 등 31권)은 이 관계가 없어 사건 근거 칩으로는 등장하지 않고, 대신 추정연도 단독 마커로 배치된다(아래 "사건의 근거" 참조). 이 31권은 별도의 **book_events 오버레이**(아래 항목)로 "집필 배경·저자·직접 다루는" 사건과 약하게 연결되어 마커 행에 사건 칩이 표시되지만, 이는 `CONTAINS_BOOK`(권위 그래프·구절 교집합)과 별개의 추정 연결이다.

## Character Trait (인물 성품)

Person 노드에 주입되는 속성 `traits` (JSON 문자열 배열). 각 항목: `{trait: "겸손", verse_ref: "민 12:3", description: "..."}`. LLM(Claude API)으로 생성 후 수동 검수, `data/character_traits/people.json` → `inject_person_traits.py`로 Neo4j 주입.

**성품의 정의 (task#157)**: 시간·상황을 관통해 반복 확인되는 **지속적 인격 특질** — 미덕과 결함을 모두 포함한다(성경은 인물을 미화하지 않으므로 다윗의 통회·야곱의 기만처럼 결함도 정직하게 싣는다). 행위·사건(예배·찬양), 칭호·신분(하나님의 마음·메시아 계보), 은사·능력(괴력·예언), 시기·이력(말년의 타락)은 성품이 아니다 — 행위는 성품의 *증거*로 verse_ref·description에만 담는다. 라벨은 **통제 어휘**(미덕 24+결함 8) 안에서만 쓰며, 정본 규칙·어휘 표는 `data/character_traits/AUTHORING.md`, 기계검증은 `validate_traits.py`.

## Book Context (권별 컨텍스트)

각 Book의 시대적 배경·주제·대표구절을 담는 정적 JSON (`data/book_context/books.json`). LLM(Claude API)으로 생성 후 수동 검수. `inject_book_context.py`로 Book 노드 속성에 주입. Verse 텍스트(대표구절·인물 성품 인용절)는 **빌드타임에 getbible에서 한국어(`korean`)+영어(`kjv`)로 미리 받아 데이터에 함께 저장**한다(`generate_verse_text.py`, ADR-0003) — 런타임 외부 fetch 없음. 단 **사건 근거 절 본문은 인라인이 아니라 정본 절 사전**(`data/bible/verses.json`, 전권 31,103절 프리베이크)에서 `/event/{id}/verses` 응답 시 합성한다(ADR-0015 — event_verses는 verseID 참조만 보유). Book의 대표구절 본문은 `keyVerseTextKo`/`keyVerseTextEn` 속성으로 주입된다.

## Place Context (장소 컨텍스트)

좌표가 있어 지도에 뜨는 장소(43개)의 **성경적 배경 산문(`background`)·대표구절(`keyVerse`)**을 담는 정적 JSON (`data/place_context/places.json`, dict 키=장소 id). **Book Context의 장소판** — 구조·파이프라인이 동일하다: LLM 직접 생성(ADR-0006, `place_coords`의 `note`를 시드로) → 대표구절 본문 빌드타임 프리베이크(`generate_verse_text.py`의 `bake_place_context`, `keyVerseTextKo`/`keyVerseTextEn`) → `inject_place_context.py`로 Place 노드에 4개 필드(`background`/`keyVerse`/`keyVerseTextKo`/`keyVerseTextEn`)만 SET. **실제 노드의 서술 보강이라 오버레이가 아니라 주입**한다(추정 독립 데이터만 오버레이하는 ADR-0004 원칙 — book_context와 동일 선례). SidePanel은 `node.label === 'Place'` 블록에서 "장소 배경"·"대표 구절"(한/영 탭) 섹션으로 렌더한다. 기존 `note` 필드는 시드로만 쓰고 보존(미렌더).

## 추정연도 (placementYear)

사건-구절 교집합(`CONTAINS_BOOK`)이 없어 `startYear`를 못 얻는 31권에 부여하는 타임라인 배치 연도 (`data/book_years_approx/books.json`의 `placementYear`, `yearApprox=true`로 표시). **기준은 "작성(저작) 시점"이 아니라 "그 책이 속하는 사건/내용 시대"** — 정확연도 책의 `startYear`(그 책이 기록한 사건들의 `startDate` 최소~최대를 `load_books.py`가 집계)와 **같은 의미축**이다. 즉 추정/정확은 *의미*가 다른 게 아니라 *도출 방법*만 다르다 (정확 = 사건 집계 자동, 추정 = 사건이 없어 수동 추정). 구약 내러티브·시가서는 배경 시대로 배치하고(작성 시점은 `basis`에 곁들이되 배치엔 안 씀), 신약 서신서·계시록은 "쓰여 보내진 순간이 곧 그 책의 시대"라 결과적으로 작성 시점과 일치한다. 사건 연결(아래 Book Events ⚡)과는 **독립축** — 연결이 있어도 연도는 여전히 추정이다.

## 사건 연대 (startDate)

Event 노드의 발생 시점 속성. **혼재 형식의 문자열**이다 — 연도만("-4003", "30"), 연-월("-1451-01"), 연-월-일 3파트가 공존하고 BC는 음수 접두. 따라서 **문자열 사전순 정렬은 BC 연도를 역전**시킨다("-1451" < "-4003"). 정렬·비교·필터에 쓸 때는 반드시 연도를 파싱해 수치로 다룬다(부호 분리 후 첫 파트를 정수화 — 프론트 `dates.js`의 `parseYear`, 백엔드 nodes.py `_year`가 같은 규칙). 책의 `startYear`는 이 값을 집계해 파생된다(추정연도 항목 참조).

**정본 연대계는 현대 보수 연대계**다(출애굽 BC 1446 · 다윗 통치 1010–970 · 성전 착공 966, 분열왕국은 Thiele 왕 연대 — ADR-0014; 신약 앵커는 십자가 AD 33 — ADR-260722-070154). theographic 원본 연대는 구약이 Ussher계(출애굽 1491 등)·신약이 십자가 AD 30 기준으로 기록돼 있어 보수계로 저작된 [[저작-사건-authored-event]]·인물 여정과 한 타임라인에서 충돌했고, 교정 오버레이(`data/date_corrections/`, 구약 113 + 신약 138 = 251건)가 원본 이벤트의 `startDate`/`sortKey`를 정본계로 재정렬한다(task#158 구약, #237·238 신약 — 판정표 `.forge/reports/nt-corrections-*.md`). 신약 이관 규약: 원본·저작이 같은 장면이면 저작 앵커 **인접** 배치, 복음서 배열 충돌(마태 주제별 vs 마가·누가 연대순)은 이중 증언 우선, 연도 라벨은 인접 저작 앵커 라벨 준수. Person의 `birthYear`/`deathYear`는 UI 미사용이라 Ussher계로 잔존한다(노출 전 ADR-0014 재검토). **교정은 오버레이라 로더(load_theographic 등) 재실행이 되돌린다 — 재적재 후 `inject_date_corrections.py` 재실행 필수.**

**`sortKey`와 `startDate`는 별개의 두 정렬 축이며 서로 역전되면 안 된다.** `sortKey`는 서사 순서(투어 정차지·여정 정렬)를, `startDate`는 화면에 뜨는 연도를 결정하므로, 통합 시간축(여러 인물 파일을 `sortKey`로 정렬)에서 인접쌍의 `startDate`가 역전되면 정렬과 연도 라벨이 서로 다른 이야기를 한다. **새 사건을 저작할 때 `startDate`를 `sortKey`의 정수부에서 공식으로 뽑지 말고, 인접 앵커의 실측 `startDate` 사이에 들어가게 하라** — 기존 데이터는 절삭·내림 어느 쪽으로도 일관되지 않는다(`kadesh-spies` -1444.5 / sd -1445는 내림, `plains-moab` -1406.95 / sd -1406은 절삭). task#265에서 정수부 공식을 적용한 결과 기브롯 핫다아와·미리암 비방이 `sortKey`로는 가데스 정탐보다 앞이면서 `startDate`로는 뒤가 되는 역전이 생겼다([[저작-사건-authored-event]]의 앵커 프레임 정합과 짝을 이루는 규칙).

## Book Events (책-사건 연결 오버레이)

추정연도 책(31권 — `startYear` 없어 `CONTAINS_BOOK`이 없는 서신서·시편·잠언 등)을 타임라인 사건에 약하게 연결하는 정적 JSON (`data/book_events/books.json`, 형식 `{ "<bookId>": ["<eventId>", ...] }`). 연결 기준은 **집필 배경**(서신서→사도행전 사건)·**저자**(시편→다윗 통치)·**직접 다루는 사건**(역대하→솔로몬·유다 왕). LLM(Claude API)으로 생성하는 추정 데이터(`generate_book_events.py`)라 **Neo4j에 주입하지 않고** `/books` 엔드포인트가 런타임에 오버레이해 각 책에 `events` 배열로 실어 보낸다(`book_years_approx`와 동일한 분리 원칙 — 추정·권위 낮은 데이터는 권위 그래프 밖 오버레이로 유지, inject·재빌드 불필요). TimelineView의 책 마커 행은 이 `events`를 ⚡ Event색 칩으로 표시하고(클릭 시 그 사건 선택), 데이터가 없는 사건(예: AD57 이후 후기 서신·계시록, 포로귀환)은 빈 배열이라 칩이 없다. **CONTAINS_BOOK의 "사건의 근거"(구절 교집합) 의미와 무관** — 이 ⚡ 연결이 사건 행의 📖 근거 칩·구절 레이어에 합류하는 것은 **그 (권, 사건) 쌍이 event_verses에 근거 구절을 가질 때만**이다(예: 옥중서신의 "나의 매임" 자기 언급). 구절 근거가 없는 ⚡ 연결은 책 마커 행의 ⚡ 칩으로만 남고 사건의 근거로 승격되지 않는다 — **단 미보유 쌍은 0건이며, 이는 특정 시점의 관측치가 아니라 `scripts/check.sh`의 `validate_approx_book_verses`가 매 배포 강제하는 불변식이다**(task#274 — `VERSE_MAP` ↔ `book_events`를 죽은 키·미커버 쌍 양방향으로 대조하며, 어느 쪽으로 갈라져도 게이트가 비0으로 막는다 → ADR `260820-003946`). 그 구절은 `generate_approx_book_verses.py`의 `VERSE_MAP`이 권마다 **집필 배경을 드러내는 서문 절**(대개 1:1~1:2)로 부여하며, 그것이 사건 자체를 서술하지 않아도(야고보서 1:1이 예루살렘 공의회를 언급하지 않듯) 이 부류 전체에 일관되게 적용되는 설계다.

## 저작 사건 (Authored Event)

`startDate`를 가진 theographic 사건이 AD57(바울 1차 로마 투옥)에서 끊겨, 그 이후 쓰인 후기 서신·계시록(추정연도 31권 중 10권: 디모데전후·디도·벧전후·유다·요한1~3·계시록)이 매달릴 타임라인 사건이 그래프에 없다. 이를 메우려고 **그 책들이 쓰인 정황을 거꾸로 도출해 만든 추정 사건**이 저작 사건이다 — 성경 본문 밖 자유 역사 사건(예 예루살렘 함락 AD70)이 아니라 **고아 책 기반**(예: 계시록→요한의 밧모섬 유배(계 1:9), 디모데후서→바울 로마 2차 투옥·순교, 베드로전후→베드로 로마 사역·순교, 요한1~3→요한 에베소 만년 사역). theographic 검증 사건과 달리 LLM/수동 저작이라 권위가 낮다.

**오버레이가 아니라 Neo4j `Event` 노드로 적재하되 `authored:true`로 마킹한다 (ADR-0005)** — 사건은 `/events`·`/node/{id}`·`/node/{id}/places`·사건 링이 소비하는 **일급 엔티티**라, 오버레이로만 두면 ⚡ 칩 클릭 시 `/node/{id}`가 404가 되어 SidePanel·지도·링이 깨지기 때문(이 점이 *연도·링크* 오버레이를 다룬 ADR-0004와 갈리는 지점). `/events`가 `authored` 플래그를 노출하고 TimelineView가 `추정` 배지 + 범위 라벨로 표시한다. theographic ID(`rec` 접두)가 없어 `authored-<slug>` 식별자를 `theographic_id`에 부여한다. **`CONTAINS_BOOK`(📖 근거)을 갖지 않으므로** 사건 근거 칩을 오염시키지 않고, 후기 10권과는 **book_events 오버레이(⚡)** 로 연결된다(`CONTAINS_BOOK`이 아니라). 기존 Place(로마·밧모·에베소)·Person(바울·베드로·요한)에 `OCCURS_AT`/`HAS_PARTICIPANT`로 연결해 지도·링을 살린다. 연도는 정렬용 단일 `sortKey` + 표시용 범위 라벨(`yearLabel`)로 둔다.

## 저작 인물 (Authored Person)

성경인물탐험에 큐레이션하려는 주인공이지만 Theographic 그래프에 Person 노드가 없는 인물. 기존 큐레이션 16인은 실제 Theographic `rec` id를 재사용하지만, 재사용할 노드가 없으면 **마킹된 authored Person 노드를 새로 만든다 (ADR-0008)**. **단, theographic에 검증 가능한 대응 실레코드가 있으면(가족 링크의 성경 사실 일치로 판정) 저작 노드가 아니라 그 실레코드가 정식 신원이다 — 저작 노드는 원본에 아예 없을 때만 만들고 유지한다(ADR-0022, 사울·룻·기드온 등 11명 이관; 다니엘·엘리야만 저작 잔존).** `data/authored_persons/people.json` → `load_authored_persons.py`가 `MERGE (p:Person {theographic_id})` + `authored:true` + `name`/`nameKo`로 멱등 적재. 식별자는 `authored-person-<slug>`(저작 사건 `authored-<slug>`·저작 장소 `authored-place-<name>`와 같은 계열). **적재 순서 제약**: authored Person이 `load_person_events.py`보다 먼저 적재돼야 인물 여정 사건의 `HAS_PARTICIPANT` MATCH가 성립한다. authored **사건의 주변 참여자**(네로·에스더 등 — 카드·여정 없음)는 이 대상이 아니라 여전히 노드 없이 둔다(ADR-0005의 경계). 카드·여정·SidePanel·지도가 일급 Person으로 소비하지만 traits 부여는 별도 enrich 경로다.

**MERGE 로더의 추가·제거 비대칭**: `load_person_events.py`(및 authored 로더 계열)는 노드·간선을 `MERGE`만 한다 — 여정 사건·참여자 **추가**는 `data/*` 파일 편집 → 재적재로 반영되나(멱등), 관계형 필드 **제거**(`participants`에서 한 명 빼기 등)는 재적재로 사라지지 않아 **기존 간선을 Neo4j에서 직접 DELETE**해야 반영된다(이후 재적재 시 JSON에 없어 재생성 안 됨 = 멱등). 새 여정 사건의 완전 반영은 **①파일 편집 ②`load_person_events.py` 적재 ③api 재시작** 3단 세트이며, 적재 스크립트는 api 컨테이너에 없어(app·data만 복사) **호스트 python**(neo4j 127.0.0.1:7687 + `.env` 비밀번호)으로 실행한다. → [[여정-journey]]

## 화면 단계 (Stage)

앱 최상위 화면 전환 단위. 주요 단계 — **인물 허브(hub)**: 큐레이션 인물 카드 목록, 시작 화면(단, [[인트로-site-intro]]가 켜져 있으면 무해시 진입에서 인트로가 먼저 보인다). **탐험(explore)**: 선택한 인물의 여정 또는 [[테마 투어]]의 지도·타임라인 — 인물·투어 중 **하나가** 정차지를 공급하며 둘은 상호배타다(투어 구동 시 선택 인물 없음). **테마 투어 목록(tours)**: 테마 투어 카드 목록, 허브에서 진입. **성경 책 둘러보기(overview)**: 66권을 구약/신약·장르(율법서·역사서 등 10범주)로 훑는 화면. 사용자에게 노출되는 라벨은 **"성경 책 둘러보기"로 통일**한다 — "성경 개요"는 같은 단계를 가리키던 옛 표기로, 진입 버튼("성경 책 둘러보기")과 어긋나 혼동을 주므로 쓰지 않는다.

**stage 조건부 렌더 = 언마운트/리마운트**: App.jsx가 각 단계를 `{activeStage === 'x' && …}`로 조건부 렌더하므로 단계 이탈 시 그 화면 컴포넌트가 언마운트된다 — 스크롤 위치처럼 **세션 내내 유지해야 하는 상태는 컴포넌트 state로 못 지키고 모듈 스코프 메모리**(예: `scrollMemory.js`·`hubEntrancePlayed`)에 둬야 리마운트를 견딘다. 또한 인앱 "← 뒤로" 버튼은 popstate가 아니라 **전진 push**라(ADR-0010) `history.state`로도 인앱 뒤로 복원이 안 된다 — 뒤로 상태 복원 작업은 "그 뒤로가 popstate냐 전진 push냐"를 먼저 판별해 저장소를 고른다(모듈 스코프 메모리가 인앱·OS 뒤로 둘 다 커버).

**스테이지를 파일로 분리할 땐 언마운트 경계를 넘나드는 상태를 분리 컴포넌트가 소유하지 않는다**: 단계 하나를 별 컴포넌트 파일로 빼면 그 단계만 쓰는 상태도 함께 옮기는 게 자연스러워 보이지만, 조건부 렌더는 언마운트라 **그 단계를 벗어나도 유지돼야 하는 상태는 소실된다**(예: 탐험의 "족보" 탭은 탭 전환이 아니라 전용 단계 진입이어서 그 순간 탐험 화면이 언마운트된다 — 여정과 사용자가 고른 정차지가 날아가 복귀 시 재조회·선택 초기화가 된다). 코드만 훅으로 빼고 **수명은 언마운트를 견디는 생존 조상에 남긴다** → ADR-260801-183736.

**전역 헤더 밑 드레이프는 하위 내비 유무 두 스테이지를 함께 검증**: 책갈피 리본처럼 전역 헤더 밑에 드리우거나 덧대는 요소(ADR-0026 드레이프 관용구)는 허브(하위 내비 없음) 기준으로 설계돼, 하위 내비 바가 헤더 바로 밑에 붙는 나머지 단계(탐험·개요·책·족보·리더)에서 리본 꼬리가 탭을 덮은 선례가 있다 — 헤더 밑 드레이프/덧댐을 추가·수정할 땐 **"하위 내비 있는 단계 / 없는 단계" 두 경우를 함께 확인**한다. 드레이프 깊이는 `RIBBON_OVERHANG`를 단일 출처로 SpineHeader(리본 높이)·App(여백·패널 오프셋) 양쪽을 맞춘다(매직넘버가 흩어지면 어긋나는 결합).

## 인트로 (Site Intro)

사이트의 기능(인물 탐험·여정 지도·테마 투어·성경 책 둘러보기·가계도 등)을 소개하는 관문 화면. 특정 화면을 가리키는 주소 없이 들어온 진입에서만 대문(인물 허브)보다 먼저 보이며, 공유 링크(딥링크)로 들어온 사용자는 보지 않는다. 사용자가 끌 수 있고(끄면 허브 직행), 끈 뒤에도 소개를 다시 열람하는 경로는 남는다. **"주소 없이 들어온 진입"의 경계는 세 형태다** — 해시 없음 · `#` · `#/`. `#/`는 해시가 있지만 가리키는 화면이 없으므로 여기 속한다. 이 판정은 해시 파서가 하지 않는다: 파서는 세 형태를 모두 정상적인 허브 주소로 읽고 그 계약은 [[북마크 (Bookmark)]]·이어보기 복원과 공용이다. 따라서 "이 진입이 딥링크인가"에 답하는 곳은 전용 술어 한 곳뿐이며, 그 뜻이 두 곳으로 갈리면 인트로는 조용히 사라진다(task#281에서 실제로 그랬다 — 초기값이 인트로로 옳게 계산된 직후 딥링크 복원이 허브로 덮었다). **"대문"은 인물 허브를 가리키는 기존 용어로 유지한다** — 인트로는 대문 앞의 선택적 관문이지 대문의 대체가 아니다. → [[화면-단계-stage]]
_Avoid_: "온보딩 투어"(화면 위 코치마크 안내라는 뉘앙스 — 인트로는 독립된 소개 화면이다)

## 상세 시트 (Detail Sheet)

사용자가 선택한 대상(인물·장소·사건·성경책)의 상세 정보를 보여주는 화면 요소. **대상 종류와 무관하게 하나뿐**이다 — "인물창"·"책 상세창"·"레이어"처럼 따로 있는 게 아니라, 같은 시트가 선택 대상에 따라 담는 내용만 바꾼다. 데스크톱에선 화면 우측에서, 모바일에선 화면 아래에서 올라온다. 탐험 화면에서 지금 탐험 중인 인물 자신은 이 시트로 겹쳐 띄우지 않고(여정 흐름을 가리지 않도록) 그 외 대상을 고르면 뜬다. 허브 화면에는 선택 대상이 없어 시트가 없다. → [[화면-단계-stage]], [[selectednode]]

## selectedNode

프론트엔드 전역 상태. 현재 사용자가 선택한 엔티티의 `theographic_id`와 레이블(Person/Place/Event/Book)을 담는다. MapView / TimelineView 두 뷰가 이 값을 구독해 동시에 갱신된다. (GraphView는 제거됨.)

## 사건의 근거 (Scriptural Evidence)

특정 Event를 기록한 성경 본문. TimelineView의 데이터 흐름은 **연도 → 사건 → 성경권 → 성경구절**이며, 마지막 두 단계가 그 사건의 근거다. 권 단계는 `CONTAINS_BOOK`(사건 ↔ 권, 한 사건에 여러 권 가능), 구절 단계는 원천 theographic `verses`에서 사건·권별로 해석한 절들(인용 범위 + 본문)이다. 원천 theographic 사건 외에 **구절 사건(verse-event)** — 책의 *고아 구절*(어떤 Event에도 안 붙은 절)에서 도출해, 그 구절 없이는 타임라인에 안 뜰 서사에 시대 위치를 준 사건 — 도 근거 구절을 갖는데, 이들의 근거는 theographic event→verses 링크가 아니라 **그 책 고아 구절 범위에 앵커해 저작**한다(책 칩만 있고 구절이 비어 "표시할 구절이 없습니다"가 뜨던 갭을 메움). 타임라인은 사건을 척추로 두고 그 사건의 근거 권을 칩으로 붙여 보여준다. **한 사건의 근거로 어떤 권의 구절을 인정하는 기준은 두 패턴뿐이다 — (a) 평행 기사(같은 사건을 기록한 본문: 공관복음 평행 단락·역대기 평행·족보 언급), (b) 집필 정황 자기 언급(그 사건 중에 쓰인 책이 본문 안에서 그 정황을 스스로 증언: 옥중서신의 "나의 매임" 등). 어느 쪽에도 해당하지 않으면 구절을 만들지 않는다**([[구절 근거 원칙 (verse-grounded principle)]] — 외부 문헌비평 논거(저자 추정 등)는 본문 근거가 아니다). 중복 제거(dedupe)로 병합된 사건의 평행 기사 판정 범위는 남은 사건의 제목이 아니라 **병합 클러스터가 흡수한 장면 전체**다 — 예: "물 위로 걸어간 베드로"가 theographic "예수가 물 위를 걸으심"을 흡수했으므로 베드로 삽화가 없는 막 6장·요 6장의 같은 장면 기록도 이 사건의 평행 기사다. 단, 사건이 없는 책(`startYear` 없음 = `CONTAINS_BOOK` 미연결, 서신서·시편·잠언 등 31권)은 근거 칩이 아니라 추정연도(`book_years_approx`) 단독 마커로 표시되며, 사건이 없으므로 구절 근거 단계는 갖지 않고 클릭 시 권 개요만 보여준다. 다만 이 마커 행에는 **book_events 오버레이**(위 항목)로 그 책과 약하게 연결된 사건이 ⚡ 칩으로 곁들여 표시된다 — 이는 "사건의 근거"(권→사건 기록)가 아니라 책의 집필 배경·저자 맥락이라 방향·의미가 반대다.

**저작 사건의 구절 참조 표기 규칙**: `person_events`의 `context` 말미에 붙이는 참조(`(Exod 14:21–31)` 형식 — 구절 베이킹이 이 문자열을 파싱한다)는 **단일 연속 범위 하나**로 쓴다. 세미콜론·콤마로 두 구간을 적으면 `generate_person_event_verses`가 **같은 책의 두 번째 세그먼트를 무조건 드롭**한다. 진술이 두 구간에 걸치면 둘을 포함하는 단일 연속 범위로 넓히되(교차-장 허용 — `(Exod 32:1–34:28)`), 그 사이에 사건과 무관한 내용이 많이 끼어 억지 인용이 될 때는 **범위를 넓히는 대신 진술에서 그 요소를 빼라**(예: 만나 사건의 "광야 40년"은 근거가 16:35뿐이고 16:16–34에 오멜 규례·안식일 규정이 끼어 수치를 삭제하는 편이 옳았다). 그리고 **`context`에 쓴 모든 진술이 그 범위 안 본문으로 뒷받침되는지 저작 시점에 대조하라** — task#264~266에서 이 축의 위반 5건이 발견됐고 기계검증(개수·정렬·비어있지 않음)은 전부 통과한 상태였다. 같은 제약이 [[테마 투어]]의 정차지 해설(note)에도 적용된다(그 사건의 범위 밖 구절·다른 사건을 끌어오지 않는다). **그리고 베이킹된 근거 절은 `rangeLabel`이 가리키는 범위 전체를 덮어야 한다** — 라벨과 절이 갈리면 화면은 "38:1–42:6"이라 적고 본문은 1절만 보여준다(사용자에게는 근거가 *있는데 부실한* 것처럼 보이므로 비어있음보다 나쁘다). 범위 안에서 [[정본 절 사전]]에 존재하는 절 전부가 근거이며, 그 판정 오라클은 화면 본문을 합성하는 사전과 **같은 파일**이다(ADR `260821-125000`).

## 정본 절 사전 (Canonical Verse Dictionary)

정경 전권 31,103절의 본문을 `verseID`(`BBCCCVVV` 8자리) 키로 담는 단일 파일 (`data/bible/verses.json`, 절당 `{textKo, textEn}`). **성경 본문의 정본 원천**이며 두 역할을 겸한다 — (a) `GET /event/{id}/verses`가 [[사건의 근거]] 절의 본문을 응답 시점에 여기서 합성한다(`event_verses`는 `verseID` 참조만 보유 — ADR-0015. 그래서 근거 절 본문은 데이터 파일에 중복 저장되지 않는다), (b) **절의 존재 오라클** — 어떤 절이 실재하는지의 판정이 곧 이 파일의 키 존재 여부다. 장별 절 수를 따로 표로 들 필요가 없다는 뜻이며, 구절 범위 전개와 그 게이트가 둘 다 이 오라클을 쓴다(ADR `260821-125000`). 파생 결과: **이 사전에 없는 절은 근거로 셀 수 없다** — 세면 게이트는 통과하면서 화면에는 본문 없는 줄이 뜬다. Book 대표구절·인물 성품 인용절 본문은 이 축이 아니라 빌드타임 인라인 저장(getbible, ADR-0003)이라 원천이 다르다.

## 탐색 관점 (Navigation Perspective)

BibleMap 데이터를 바라보는 세 가지 중심 관점. 관점에 따라 같은 데이터가 다르게 시각화된다.

**인물 중심 (Person-centric)**: 특정 Person이 참여한 Event와 그 Event가 발생한 Place들로 해당 인물의 활동 반경을 구성한다. Person에 좌표가 없는 이유도 여기서 비롯된다 — Person은 `HAS_PARTICIPANT → Event → OCCURS_AT → Place` 경로를 통해 간접적으로 공간을 갖는다. **지도에 표시되는 장소 수는 Theographic 이벤트와 authored 이벤트를 합산해 집계된다** — 따라서 인물 대상 authored 이벤트를 추가 계획할 때는 먼저 기존 Theographic 이벤트가 연결하는 장소 수를 파악해야 실제 필요한 authored 이벤트 수를 산정할 수 있다.

**장소 중심 (Place-centric)**: 특정 Place에서 발생한 Event와 그 Event에 참여한 Person들을 조회한다. 지도 마커 클릭이 이 관점의 진입점이다.

**시대 중심 (Era/Timeline-centric)**: 특정 시기의 Event 흐름과 그에 연결된 Person·Place를 탐색한다. `Period`(= Event의 `PART_OF` 계층)가 이 관점의 정렬 축이 된다. TimelineView는 사건을 시대순으로 늘어놓고, 각 사건의 "사건의 근거"(성경권 → 구절)를 함께 보여준다.

## 여정 (Journey)

한 인물의 **시간순 사건(Event) 묶음**. 여정은 사건 하나가 아니라 사건들의 시퀀스이며, 계층은 **여정 ⊃ 사건(여러 개) ⊃ 그 사건의 근거 구절**이다 — 근거 구절은 여정에 직접 붙는 것이 아니라 여정을 구성하는 **각 사건에** 붙는다. 각 사건은 발생 장소(Place)를 통해 지도상의 한 정차지로 나타난다(좌표 없는 사건은 정차지 없이 목록에만 표시). "인물 중심 관점"의 핵심 산물로, 큐레이션 인물에 대해 정의된다. UI(JourneyList)는 이 계층을 "{인물}의 여정 · 사건 N개 → 각 사건 펼치면 구절" 아코디언으로 보여준다.

**참여자 불변식**: 여정을 구성하는 모든 사건은 **그 인물이 실제 참여자인 사건**이다 — 같은 시대·같은 무리에게 일어났더라도 그 인물이 본문에 등장하지 않는 사건(예 모세 여정에서의 발람과 발락, 민 22–24)은 그의 여정에 속하지 않는다. 이 불변식이 깨지면 여정 목록과 인물 연표가 갈린다(전자는 여정 전량, 후자는 엄격 참여자 필터). 결과로 **[[테마 투어]]가 참조할 수 있는 사건은 어떤 큐레이션 인물의 여정에 속한 사건뿐**이며, 주인공 없는 시대 사건은 투어 정차지가 될 수 없다.

**색인 불변식**: 큐레이션 인물 색인의 **정본은 `backend/app/curated.py`의 `CURATED`** — slug → `{nameKo, era}` 단일 테이블이고, 시대 표시 순서는 같은 모듈의 `ERA_ORDER`(8구간)다. 라우트는 이 모듈을 **경유만** 하며 자체 선언을 갖지 않는다. `curated.py`는 `overlays.py`와 같은 층이고 **라우트를 import하지 않으므로** 순환 import가 구조적으로 불가능하다(그래서 `family.py`가 쓰던 함수 내부 import 워크어라운드가 사라졌다). 세 집합의 관계는 **매 배포 게이트가 강제하는 불변식**이다 — `CURATED` 키 집합 == `data/person_events/*.json` 파일 집합(**양방향**: 죽은 키·미커버 파일 둘 다 위반), `data/god_reliance/*` ⊆ `CURATED`, `person_slugs/seal_slugs.json`(인장 상위집합) ∩ `CURATED` == ∅, 각 `era` ∈ `ERA_ORDER`. 갈라지면 무가드 조회가 `KeyError` → 500이 되므로 이것은 관측치가 아니라 규범이다(`validate_curated_persons`, ADR `260820-003946`). 단 게이트는 파일명 집합만 대조하므로 **손상된 JSON 자체는 아직 걸러내지 못한다**. `CURATED`는 검증기가 `ast.literal_eval`로 소스에서 직접 뽑는 대상이므로 **순수 dict 리터럴 형태를 유지해야 한다** — 컴프리헨션·프로그램적 생성으로 바꾸면 추출이 실패해 fail-closed로 배포가 막힌다.

## 테마 투어 (Themed Tour)

여러 인물의 [[여정-journey]]을 하나의 주제(시대·서사)로 엮은 큐레이션된 시간순 사건 시퀀스. 여정이 *한 인물*의 사건 묶음인 것과 달리, 테마 투어는 한 인물로는 드러나지 않는 관계(예: 사울-다윗 대립, 족장 4세대 언약)를 여러 인물의 사건을 교차해 보여준다. 계층은 여정과 동일하다 — **투어 ⊃ 사건(여러 개) ⊃ 각 사건의 근거 구절**. 각 정차지에는 **정차지 해설(stop note)** — 그 사건이 *이 테마 안에서* 갖는 의미를 서술하는 투어 관점 텍스트 — 이 붙을 수 있으며, 해설은 사건 본문(person_events)이 아니라 투어의 틀에 속한다(ADR-0028). 정차지에는 해설과 함께 [[장면 스케치]]가 붙을 수 있다. 단일 주인공이 없어, 투어를 구성하는 사건들의 참여자가 곧 그 투어의 등장인물이다. 성경 서사 척추(시대)를 따라 큐레이션되며, 각 투어는 기존 여정 사건을 재사용해 엮는다(신규 사건 저작이 아니라 순서·틀 부여). **커버리지 원칙**: 큐레이션이되 선별적 발췌가 아니다 — 투어 시대에 맞는 저작 사건은 원칙적으로 모두 포함하고, 제외는 동일 장면의 인물별 중복 시점(한 시점만 대표로 남김)과 서사에 기여 없는 순수 연대기 기록에 한한다. → [[여정-journey]], [[탐색-관점-navigation-perspective]]

## 장면 스케치 (Scene Sketch)

[[테마 투어]] 재생 중 정차지 해설 카드 상단에 함께 표시되는 **저작 삽화 시퀀스 애니메이션** — 그 사건의 장면이 양피지 위에 단계적으로 그려지고 움직이는 짧은 연출(예: 물매 돌이 날아가 골리앗이 쓰러짐). 인물 이름표·상황설명 한 줄·출처 캡션이 삽화와 한 장으로 읽히며, 어두운 장면은 강조색이 금색에서 목탄색으로 가라앉는다(무드). 정차지 해설(테마 관점 텍스트)과 역할이 다르다 — 해설이 *의미*를 말하면 장면 스케치는 *사건 자체*를 보여준다. 저작 형식·보관은 ADR-0029(투어별 JSX 코드 모듈 — 2026-08-21 개정으로 그 경계가 번들 경계이기도 하다), 선화 규약은 ADR-0025를 따른다. **얼굴은 그린다** — ADR-0025가 2026-08-21에 개정돼 장면 스케치에 한해 이목구비가 허용됐다(인물·책 인장은 초상 금지 유지). 장면이 무엇을 하는 장면인지는 시선과 표정이 말하며, 상징물만으로는 그 축이 비어 있기 때문이다. 스케치 없는 정차지도 성립하지만, **의도적으로 미저작한 정차지에 한한다** — 미저작은 검증기의 허용목록에 명시된 경우에만 성립하고, 목록에 없는 미저작은 결함으로 다룬다(저작을 잊은 정차지는 화면에 아무것도 뜨지 않으면서 오류도 남기지 않기 때문). **"커버됨"은 레지스트리에 키가 있다는 뜻이 아니라 화면에 그려진다는 뜻이다** — 스케치 모듈이 통합 레지스트리에 import·병합되지 않으면 키가 있어도 렌더되지 않고, 증상은 미저작과 완전히 같다(무음·무오류). 따라서 커버리지 판정은 키 집합 대조와 **모듈 병합 여부**를 한 세트로 본다(task#259). → [[테마 투어]]

## 붓질 단계 (Draw Step)

[[장면 스케치]]가 완성되기까지 나뉜 **그리기의 한 단위**. 한 단계 안의 선들은 서로 동시에 나타나므로, 단계가 적으면 그림이 "도장처럼" 찍히고 많으면 손으로 그려지는 것처럼 읽힌다. 단계를 무엇으로 묶을지는 **저작 판단**이다 — 의미 있는 순서(지면 → 인물의 다리 → 몸통 → 지물)를 사람이 고르며, 기계가 요소 순서대로 자동 분할하는 것은 이 판단을 대체하지 못한다(ADR-0024 개정 ②에서 자동 스태거안이 이 근거로 기각됐다). 기계가 강제하는 것은 판단이 아니라 **경계**뿐이다: 한 단계에 묶이는 선의 상한 · 장면당 단계 수의 하한 · 장면 전체가 그려지는 데 걸리는 시간의 상한. **붓질 순서는 그리기 순서이고, 레이어 소속이 아니다.** 저작된 단계 순서에서 「배경」과 「인물」을
파생하려는 시도는 실패한다 — 사무엘 순회 재판 실측 순서는 전폭 지면선 → 상단 하늘·성문(24선) →
우측 나무·집(14선) → **중앙 인물(38선)** → 좌측 사구·지팡이(36선) → **중앙 인물(83선)**로 둘이
섞여 있다. 같은 이유로 구역 주석(공개 연출의 구역 분할)도 붓질 순서에서 파생되지 않는다 — 첫 단계가
지면·수평선의 **전폭 획**이라 그 그룹의 bbox가 프레임 전체로 나온다. 레이어나 구역이 필요하면
**새 저작 표시**가 필요하다(296장면 × 태깅).

**시작 전 상태도 화면이다.** 아직 그려지지 않은 획은 `stroke-dasharray:1; stroke-dashoffset:1`이고,
라운드 캡 때문에 **점으로 보인다** — 197선 장면의 첫 프레임은 빈 종이가 아니라 50개 넘는 점이
흩뿌려진 화면이었다(2026-08-23 실서버 확인). 드로인을 "무엇이 나타나는가"로만 설계하면 이 층을
아무도 안 본다(몽타주 반려의 「사용자가 보는 첫 프레임」 교훈과 같은 계열 — ADR `260823-112504`).

마지막 항목은 [[테마 투어]] 재생의 체류 시간과 한 방향으로 묶여 있다 — 장면이 다 그려지기 전에 다음 정차지로 넘어가면 안 되므로, **장면의 시간 예산이 재생 체류 시간의 하한을 결정한다**(그 역이 아니다 — ADR `260821-174856`). → [[장면 스케치]]

## 장면 밀도 (Scene Density)

한 [[장면 스케치]]를 이루는 선의 수. 같은 규약(굵기 위계)을 지키면서도 밀도가 낮으면 그림이 막대인형으로 읽히고, 높으면 삽화로 읽힌다 — 즉 **밀도는 취향이 아니라 그림이 무엇으로 보이는지를 결정하는 축**이다. 다만 **밀도만으로는 부족하다**: 늘린 선이 옅은 배경 획이면 개수는 3.6배가 돼도 화면 인상은 그만큼 달라지지 않는다(파일럿 실측 — 구조 비율이 원본 40%에서 8%로 희석). 그래서 밀도와 함께 [[구조 선]]의 비율을 본다. 밀도는 [[붓질 단계]] 수의 상한을 규정하기도 한다(선이 10개면 아무리 잘게 쪼개도 10단계를 넘지 못한다). 목표 밀도와 그 대가(저작량 · 번들 무게)는 ADR `260821-174855`가 정본이다.

**목표 밀도는 값이 하나로 정해진 축이 아니다.** 파일럿 3장면은 191~219선이고 나머지 293장면은 중앙값 10선이며, 규약 정본(`lib.jsx` B1)은 "단순한 장면(기본형)의 목표 40~45"와 "다인물 밀집 장면(상한형) 191~198"을 **둘 다** 적고 있다. 어느 쪽인지는 결정돼 있지 않았고, 그 미결이 정본 주석에서 한쪽으로 조용히 기울어 있었다 — 위임된 정본은 미결을 미결로 표시해야 한다(ADR `260822-220823`).

**최소 밀도는 판정자에 따라 두 개이고, 2026-08-22에 측정됐다**(task#305, [[조건 입력 적합성]]) — **D_human 22~27선**(사람, 카드 배율)과 **D_model 91선**(모델). 두 값이 3.4배 갈리므로 목표 밀도는 "래스터 경로를 채택하는가"에 종속되며 **여전히 미결**이다(측정 완료는 결정 완료가 아니다 — ADR `260822-220823` 2026-08-23 개정). 저작 원가는 실측 2점 회귀 `줄(D) ≈ 14.9 + 1.939·D`(293장면 현재 평균 35.1줄·10.4선 ↔ 파일럿 408줄·202.7선)로 환산한다 — 순증이 D_human 27선 ≈ 9,400줄 · 기본형 42선 ≈ 17,957줄 · D_model 91선 ≈ 45,800줄 · 상한형 203선 ≈ 109,449줄이다. **오래 인용돼 온 "약 10배(8,000 vs 78,100)"는 실측으로 정정된다** — 기본형 열이 2.2배 낮게 잡혀 있었고, 실질 결정 구간(기본형↔D_model)은 2.6배다.

**밀도가 올리는 것은 인체 판독이 아니라 장면 정보다.** 감선 계단 실측에서 22~27선만으로도 사람은 인체를 읽었고, 그 위로 선을 더할 때 늘어난 것은 **장소**(성문·산·집)와 **신원**(얼굴·후광·지팡이)이었다. 그래서 기본형과 상한형의 차이는 "사람으로 보이는가"가 아니라 **"어디서 무슨 일인지 보이는가"**다 — 원가 fork를 판단할 때 걸린 것이 무엇인지가 이 문장에 달려 있다. → [[장면 스케치]], [[조건 입력 적합성]], [[판독성]]

## 구조 선 (Structural Stroke)

[[장면 스케치]]에서 **사람·사물의 형태를 이루는 굵은 선**(굵기 2.0 이상). 배경·질감(원경 능선 · 구름 ·
지면 자갈)과 대비되는 개념이며, 둘의 비율이 [[장면 밀도]]가 못 재는 축을 잰다 — 선을 늘려도 그것이
전부 옅은 배경 획이면 그림은 달라지지 않는다. 원래 제대로 그려져 있던 장면의 구조 비율이 30~40%였고,
배경으로 채운 재작도가 8~11%로 희석됐다는 실측이 이 개념을 낳았다.

두 가지가 이 용어에 딸려 있다. 첫째, **구조 선은 연결된 조립체여야 한다** — 머리·팔·다리가 몸에서
떠 있으면 부위가 따로 논다(검증기가 2단위 이내 접촉을 강제한다). 둘째, **구조 선을 좁은 데 몰아넣으면
반대편 실패가 온다** — 인물 영역의 잉크 밀도가 1.0~1.3%를 넘으면 먹덩이가 되고, 몸통을 직사각형 +
전폭 가로대로 그리면 상자·사다리로 읽힌다. 수치 정본은 `frontend/src/sketches/lib.jsx`의 저작 규약이며,
경계로 재는 부분과 육안으로 보는 부분이 그 안에서 갈려 있다(ADR `260821-000937` 개정 · `260822-072153`).
→ [[장면 밀도]], [[붓질 단계]]

## 판독성 (Legibility)

[[장면 스케치]]가 **무엇으로 읽히는가** — 그려진 도형이 보는 쪽에게 의도한 사물로 인지되는지의 축.
[[장면 밀도]](선의 개수)와 [[구조 선]](굵은 선의 비율)을 **둘 다 만족해도 판독성은 실패할 수 있다.**
실측: 같은 장면 안에서 다윗(머리 원 + 팔다리)은 사람으로 읽혔고, 골리앗(둥근 모서리 직사각형)은
읽히지 않았다. 네 라운드 연속 되돌아온 사람 판정("사무엘이 재판하는지 모르겠다" · "골리앗 그림이
이상함")이 전부 이 축이었다.

**모호한 판독성은 빈칸이 아니라 오독으로 나타난다.** 보는 쪽은 판단을 유보하지 않고 그럴듯한 것으로
메꾼다 — 쓰러진 골리앗의 엉킨 선 뭉치를 생성 모델은 **낙타와 기수**로 읽었다(2026-08-22 실험).
사람 검수에서도 같은 일이 일어나며, 그래서 "안 읽힌다"는 신고보다 "이상하다"는 신고로 도착한다.

판독성은 **기계로 못 재는 축**으로 분류돼 왔고, 그래서 게이트를 늘리는 대신 저작자에게 보는 수단을
주는 것으로 다뤄 왔다(ADR `260822-072153`). 대리 측정 후보가 하나 있었다 — 선화를 생성 모델의 구도 조건으로
넣어 **살이 붙는지**로 판정하는 것 — 이나 task#303 S4에서 시험하고 **기각했다**: 사무엘·변화산 쌍은 구/신이
안정적으로 갈렸지만, 정작 이 가설을 낳은 골리앗 쌍에서 **시드 하나로 우열이 반전**됐다. 재현되지 않는 신호는
경계가 될 수 없다. 이 축은 여전히 사람이 본다.

**판정 배율은 카드 배율이다 — 확대하면 결함이 사라진다.** 확대 크롭으로 "머리·팔·다리가 다 있다"를
확인하면 통과로 보이고, 실제 화면에서는 언덕·상자·짐승으로 읽힌다. task#303에서 저작 에이전트가
**세 번 연속** 이 방식으로 "인체로 읽힌다"를 자기 판정했고 세 번 되돌아왔다. 확대는 원인 추적용 보조
근거이지 판정 배율이 아니다.

**실패 양식은 두 개이고, 고밀도 뭉침 가설은 기각됐다.** 이 항목은 오래 "판독 실패 = 카드 배율에서 부위들이
하나의 매스로 뭉치는 것"이라고 적어 왔다. task#305가 감선 계단으로 밀도를 8단계 훑어 재보니 그 뭉침은
**197선·192선(전체 밀도)에서도 관측되지 않았다** — 굵기 위계가 지켜지는 한 밀도 상향은 인체 판독을 해치지
않는다. 실제로 잡힌 실패 양식은 **저밀도 쪽**이었다: ① **부위 부유**(12선 계단에서 머리 원 3개가 몸 없이
떠 있다 — [[구조 선]]의 "연결된 조립체" 요구와 같은 결함), ② **인물 소실**(3·13선 계단에서 인물 절반이
사라진다). 뭉침은 밀도의 함수가 아니라 **좁은 데 구조 선을 몰아넣었을 때** 오는 것이므로([[구조 선]]의
잉크 밀도 1.0~1.3% 상한) 두 원인을 섞어 쓰지 않는다.
→ [[장면 밀도]], [[구조 선]], [[장면 스케치]], [[동시 진행 선 수]]

## 조건 입력 적합성 (Condition Fitness)

[[장면 스케치]]의 선화가 **생성 모델의 구도 조건(ControlNet)으로서 얼마나 잘 작동하는가**. [[판독성]]과
형제 축이지만 **판정자가 사람이 아니라 모델**이고, 그래서 같은 선화가 한쪽은 통과하고 다른 쪽은 실패할 수 있다.
실패는 판독성과 같은 얼굴로 온다 — 빈칸이 아니라 오독이다(쓰러진 골리앗의 선 뭉치를 모델이 **낙타와 기수**로,
45선 변화산의 모세·엘리야를 **가로등**으로 읽었다).

두 축이 갈리는 이유는 **모델이 메꿔 주는 것이 있다**는 데 있다. 래스터 경로에서 선화는 사용자에게 보이지 않는
빌드타임 입력이고, 얼굴 디테일은 IP-Adapter 레퍼런스가, 살과 음영은 모델이 담당한다. 그래서 조건 입력에는
사람이 카드 배율에서 읽을 만큼의 밀도가 필요하지 않을 수 있다 — 필요한 것은 인물 수가 세어지고 자세·규모가
파악되는 것이다. 반대 방향도 가능하다(모델이 구도를 잡는 데 사람은 필요 없는 배경 획을 요구할 수 있다).

**그래서 최소 밀도는 하나가 아니라 둘이다** — 사람이 판정자인 값과 모델이 판정자인 값. 이 축을 [[판독성]]의
**대리 게이트**로 쓰는 안은 시험하고 기각했다 — 골리앗 쌍에서 시드 하나로 우열이 반전됐다(task#303 S4).
기각된 것은 "자동 게이트로 쓰는 것"이고, 일회성 측정과 정성적 저작 피드백으로는 유용하다.

**2026-08-22 실측(task#305): D_model = 91선, 단 장면 유형에 따라 도달 불가.** 파일럿 2장면에서 굵기 임계로
선을 깎아 밀도 계단을 만들고 시드 3개 전부 통과를 기준으로 판정했다(동결 설정 · IP-Adapter 없이 밀도 축만 분리).
- **사무엘(4인, 나란히 서 있음)**: 36·50선 실패 → **91선 통과**, 129·197 통과. 품질 평탄점도 91선이다 —
  그 위로는 장면 정보만 늘고 인체 육화 품질은 평탄하다.
- **변화산(6인, 중앙 주역)**: 38~192선 **전 계단 실패.** 최상단에서 주변 5인은 얼굴까지 육화되는데
  **중앙 주역만 3시드 모두 얼굴 없는 천 드레이프로 남는다.**

즉 **D_model은 단일 숫자가 아니다** — 도달 불가 영역이 있고, 그 영역은 밀도 축이 아니라 **자세·구도** 축에
있다(팔을 펼친 자세가 배경 능선과 합쳐져 실루엣이 천막으로 읽힌다 — [[판독성]]의 "모호함은 오독으로
나타난다"와 같은 기제이며, task#303의 "완전 수평 자세는 원리적으로 어렵다"의 모델 축 대응물이다).
**조건 입력의 상위 제약은 밀도가 아니라 구도다.** 이것은 위에 이미 적힌 원리적 제약(IP-Adapter는 화면
전역에 적용돼 다인물에 인물별 얼굴을 줄 수 없다)과 같은 다인물 15% 구간을 가리킨다(ADR `260822-111304`
2026-08-23 개정). D_human(22~27선)과의 격차 3.4배가 293장면 저작의 원가 fork를 지배한다.

**2026-08-23 개정 — 이 축의 목적이 바뀌면 값도 바뀐다.** ADR `260823-112503`이 래스터의 구조를
「저작 잉크 + 생성 [[채색층]]」으로 확정하면서, 조건 입력의 임무가 **"모델이 인체를 육화시키기"에서
"색을 옳은 자리에 두기"로 축소**됐다. 위 D_model 91선은 전자의 값이고, 후자의 최소 밀도는 아무도
재지 않았다 — 이 항목이 오래 "최소 밀도는 둘"이라 적어 온 프레임에 **세 번째 축(D_color)**이 붙는다.
293장면 원가 fork를 지배하는 값이 D_model에서 D_color로 옮겨갈 수 있으므로, 전면 확대 판단 전에
재야 한다(파일럿의 비목표).

**2026-08-24 재개정 — 목적이 또 바뀌었고, 이번엔 두 축이 남았다.** ADR `260824-002411`이 매체 교체를
채택해 [[채색층]] 2층 구조를 뒤집으면서, 조건 입력의 임무가 「색을 옳은 자리에 두기」(D_color)에서
**「AI가 이 장면을 이 구도로 그리게 하기」**로 되돌아왔다. 형태를 모델이 그리므로 요구가 D_color보다
높고 D_model 쪽에 가깝다. 다만 **D_model 91선을 그대로 상속하지 않는다** — 그 값은 **동결 강도**에서
나왔고, **밀도 × ControlNet 강도의 2차원을 아무도 재지 않았다**(task#305는 강도를 고정하고 밀도 축만
분리했다). 낮은 밀도 + 낮은 강도에서 모델이 구도만 참고하고 자유롭게 그리는 영역이 있을 수 있으므로,
이 축의 값은 **단일 숫자가 아니라 (밀도, 강도) 쌍**이다. 그 쌍을 [[콘티]] 최소 밀도 **D_conti**로 부르고
task#308이 쟀다. **이 값 없이 291장면 저작에 착수하지 않는다**(되돌리기가 재작도이므로 — ADR
`260824-002411`).

**⚠ 2026-08-24 정정 — 아래 「도달 불가」 결론은 폐기한다(측정 입력 결함).** 조건 입력을 `--at 1000000`
(연출 종료)에서 찍었는데, `GoliathScene`은 **10.55초에 상세 골리앗(88선: 투구·얼굴·이중선 팔다리·창·
방패)을 30선짜리 단순화 쓰러진 자세로 교체 페이드**한다(소스 주석이 명시: 「회전이 멈추는 즉시 아래
쓰러진 자세로 교체 페이드한다」). 그래서 **모델은 저작된 거인을 한 번도 보지 못했다.** 교체가 opacity라
`render_scene.py`의 계수기(visibility만 봄)는 사라진 88선을 「보이는 획」으로 셌고, 내가 넣은
`post_performance` 단정도 그 때문에 통과했다 — **거짓 보증**이었다(계수기는 opacity 인지로 수정했고,
이제 유령 선 수를 경고로 낸다). 실측: `--at 1000000`은 218선 중 **잉크 130선**, `--at 9000`은 **잉크 188선**.
**정정 후 재시험(3장, seed 11)**: `--at 9000` 조건 입력에서 **cn 0.6·0.8은 판정 3문항을 전부 통과**한다
— 투구·방패·창을 갖춘 거인이 우측에, 소년이 좌측에, 규모 대비까지 콘티대로 나온다(cn 0.4만 여전히
실패 — 거인이 바위 절벽으로 흡수). 근거: `.forge/reports/storyboard-density/validate/at9000-cn*.png`.
따라서 **D_conti는 도달 가능하며, 값은 미측정 상태로 되돌아간다**(격자를 올바른 조건 입력으로 다시
열어야 한다 — 계단도 total이 아니라 **잉크 선 수**로 다시 파생해야 한다). 아래 원가표의 「D_model 91선
기준 마감」도 함께 보류한다.

**교훈 — 「연출 종료 후」는 「완성 상태」와 같지 않다.** FINDINGS 규칙 ①은 *드로인 도중의 미완성 선*을
막으려고 쓰였는데, 교체 페이드가 있는 장면에서는 종료 시점이 **저작자가 의도적으로 단순화한 상태**다.
조건 입력의 시각은 「끝」이 아니라 **「잉크가 최대인 순간」**으로 골라야 한다.

**(폐기됨) 2026-08-24 1차 측정 — D_conti는 감선 축에서 도달 불가였고, 지배 변수가 밀도가 아니었다**(task#308,
`.forge/reports/storyboard-density/`). `GoliathScene`(218선) 하나를 밀도 5단(218·110·57·32·20) ×
ControlNet 강도 3단(0.4·0.6·0.8) × 시드 3개 = **45장**으로 열었고, **통과 칸이 0개**다. 판정 문항은
셋(다윗 있는가 · 골리앗 있는가 · 좌우 배치·규모 대비가 맞는가)이고 3시드 전부 통과가 칸의 기준이다.
- **다윗은 41/45칸에서 정상 육화했고, 골리앗은 45/45칸 전부 실패했다.** 같은 그림·같은 밀도·같은
  강도인데 한 인물은 되고 한 인물은 안 된다 — 그래서 **장면 밀도는 이 실패를 설명하지 못한다.**
- 실패 양상이 강도에 따라 **두 갈래**다. 저강도(0.4~0.6)에서는 거인의 선이 **지형·천·풍선으로 흡수**돼
  우반부에 인물이 아예 없고, 고강도(0.8)에서는 거인 자리가 **막대 골격으로 문자 재현**돼 살이 붙지
  않는다. 즉 「구도만 참고하고 자유롭게 그리는 영역」과 「구도를 따르되 육화하는 영역」 **사이의 창이
  이 장면에는 없다.** 강도를 올려 얻는 것은 육화가 아니라 트레이싱이다.
- 두 인물을 가른 것은 **인물별 선 수와 자세**다. 다윗은 몸통·옷·머리로 선이 뭉쳐 있고 서 있는 자세이며,
  골리앗은 **긴 직선 몇 개 + 원 하나**로 쓰러지는 자세다(전체 218선에서도 그렇다 — 감선이 만든 조건이
  아니라 **저작 원본의 조건**이다). 그래서 D_conti를 **장면 단위 (밀도, 강도) 쌍**으로 묻는 프레임 자체가
  이 장면에서는 답을 못 낸다 — 필요한 것은 **인물당 최소 선 수와 자세 제약**이다(별건).
**2026-08-24 재개정 (task#314) — (밀도, 강도) 쌍에 **「조건의 종류」**가 붙고, **굵기**가 새 축으로 선다.**

위 재개정이 이 축의 값을 「단일 숫자가 아니라 (밀도, 강도) 쌍」으로 넓혔는데, 파일럿이 그 쌍조차
**조건의 종류마다 다르다**는 것을 보였다. 같은 파이프라인 안에 조건이 두 종류 있다 —
**두상 조건**(인물 정본 1층, 4~8선)과 **장면 콘티**(잉크 188선). task#308이 후자에서 검증한 `cn 0.8`을
전자에 그대로 쓰자 **빈 타원**이 나왔다. 프롬프트를 한 글자도 안 바꾸고 강도만 내리자
빈 타원 → 윤곽 얼굴 → 완성 초상으로 갈렸다.

**정본화된 두 값: `PERSON_CN = 0.3` · `SCENE_CN = 0.8`.** 중간값 0.5는 **두 인물 모두 실패하되 방향이
다르다** — 다윗은 원의 둥긂이 유아 비례를 강제하고, 골리앗은 원이 **면갑으로 닫힌다**. 둘 다
「정본의 원을 얼굴의 경계로 문자 그대로 따르는」 같은 기제이고, 0.3에서 비로소 원이 **「머리가 여기
있다」는 힌트**가 된다. 선이 적은 조건에서 강도를 올려 얻는 것은 육화가 아니라 **트레이싱**이다.

**그리고 새 축 — 조건 입력의 굵기는 화면용 굵기와 다른 값이다.** 정본 머리 8단위에 구조 선 2.6단위
(**폭의 32%**)를 그대로 2값화해 1024px로 키우면 100px대 흰 띠가 되고, **다윗의 곱슬 8선이 한 덩어리로
뭉개진다** — 1층이 나르기로 한 실루엣이 조건 입력 단계에서 **이미 소실**된 것이다. 캡처 시점에만 균일한
얇은 굵기(`THIN_SW = 0.15`)로 덮어 **기하만** 남긴다(정본 소스는 건드리지 않는다 — 굵기는 화면용으로 옳다).

**⚠ 이 소실은 게이트가 전부 초록인 채로 일어났다.** `text_nodes: 0`은 **SVG DOM을 세지 래스터에 구워진
형태를 못 본다** — 측정한 층과 결함이 난 층이 달랐다. 조건 입력의 품질을 묻는 불변식은 소스가 아니라
**구워진 결과**에서 재야 한다. 결정 정본은 ADR `260824-191250`.

## 채색층 (Color Layer)

[[장면 스케치]]의 저작 잉크 **아래**에 놓이는 생성 래스터 층. 그림의 형태·구도·얼굴은 여전히 손저작
선화가 결정하고, 채색층은 **선 안을 칠하는 것**만 담당한다 — 그래서 원본 생성물에서 **선 성분을 지운
뒤**(형태학적 닫힘) 쓴다. 지우지 않으면 생성물의 자기 선이 저작 잉크와 겹쳐 두 벌의 선이 싸우고,
결과가 "스케치를 색칠한 것"이 아니라 **"다른 그림으로 교체된 것"**으로 읽힌다(2026-08-23 사람 판정:
「스케치와 최종결과물이 너무 다름」).

이 층의 도입이 [[테마 투어]] 연출을 웹툰 파이프라인 순서로 정렬한다 — 펜선(드로인) 완주 → 채색 →
식자. 저작 잉크가 **런타임 자산으로 잔존**하므로 매체 교체가 아니라 **가산**이며, 선화는 "모델을
조건화할 만큼"이 아니라 **"사람이 볼 만큼"** 좋아야 한다. 되돌리기 비싼 이유와 맞바꾼 것은
ADR `260823-112503`, 연출 순서는 ADR `260823-112504`가 정본이다.

**2026-08-24 — 이 구조는 채택되지 않았다.** ADR `260824-002411`이 매체 교체를 택해 저작 잉크를 화면에서
내렸다. 기각 사유는 원가가 아니라 **목표 화풍과의 모순**이다 — 사용자가 목표로 제시한 생성 이미지에는
저작 잉크의 굵은 먹선이 없으므로, 잉크를 남기는 것이 오히려 양식 불일치를 만든다. 이 항목의 실측
(선 성분 제거 방법 · 두 벌의 선이 싸운다 · 웹툰 순서 정렬)은 유효하고, **선 성분 제거는 [[콘티]] 경로에서
「생성물에서 선화 층만 뽑기」의 역연산으로 재사용된다.**

## 콘티 (Storyboard)

[[테마 투어]] 장면의 **구도를 지시하는 손저작 선화** — 형식은 [[장면 스케치]]와 같은 stroke-only SVG이나
**사용자 화면에 노출되지 않는다.** 빌드타임에 생성 모델의 ControlNet 조건 입력으로만 쓰이고, 사용자가
보는 그림은 그것을 읽은 생성 래스터다. 웹툰 제작 순서(콘티 → 펜선 → 채색 → 식자)의 **앞단계**이며,
ADR `260823-112504`가 2026-08-23 개정에서 「앞단계는 이 ADR이 정하지 않았고 미결」로 남긴 자리를
ADR `260824-002411`이 이 용어로 채운다.

**콘티가 존재하는 이유는 프롬프트가 구도를 지시하지 못한다는 실측이다** — 「좌측 소년·우측 거인·사이
여백」을 전부 무시하고 골리앗을 아예 그리지 않았다(`.forge/reports/raster-pilot/FINDINGS.md`). 글로 하는
지시가 실패했으므로 그림으로 지시한다.

**[[장면 스케치]]와의 차이는 형식이 아니라 판정자다.** 장면 스케치는 사람이 보는 그림이므로
[[판독성]]이 품질 축이고, 콘티는 모델만 읽으므로 [[조건 입력 적합성]]이 품질 축이다. 그래서 요구 밀도가
다르다 — 291장면을 「사람이 볼 만큼」이 아니라 **「AI가 읽을 만큼」**만 저작한다. 그 최소치
**D_conti**는 (밀도, ControlNet 강도) 쌍이고 **여전히 미측정**이다. task#308의 1차 측정은 45칸 전부
실패해 「도달 불가」로 나왔으나, **그 결론은 2026-08-24에 폐기됐다** — 조건 입력을 연출 종료 시점에서
찍는 바람에 상세 골리앗 88선이 단순화 쓰러진 자세 30선으로 교체된 그림을 넣고 있었다(경위는
[[조건 입력 적합성]] 2026-08-24 정정). 올바른 시각(`--at 9000`)으로 다시 넣으면 cn 0.6·0.8이 통과하므로
**도달 가능**하고, 정확한 (밀도, 강도) 쌍은 격자를 다시 열어야 나온다.
아래 D_model 91선 기준 마감은 **그때까지 보류**한다.

**⚠ 그리고 재측정은 설정화 처분 뒤에 와야 한다 — 순서 의존(2026-08-24).** task#308의 45장은
**IP-Adapter도 얼굴 레퍼런스도 없이** 돌았다(생성물마다 다윗이 다른 아이다). 그래서 그 측정이 물은 것은
「정본 다윗을 이 구도에 놓는 최소 밀도」가 아니라 **「모델이 그럴듯한 인물을 지어내게 하는 최소 밀도」**다.
레퍼런스가 정체성을 나르면 콘티는 **구도만** 나르면 되므로 요구 밀도가 내려간다 — 즉 레퍼런스 없이 잰
값은 **다른 파이프라인의 상한**이고, 설정화를 세우기 전에 다시 재도 같은 성질의 값이 나온다.
웹툰 전체 단계에서 **설정이 콘티보다 앞**이라는 것은 이미 사람 판정과 ADR 두 건이 세워 둔 규율이다
(ADR `260823-142107` · `260823-112504` 2026-08-23 부분 개정 — *「그 앞단계인 인물을 먼저 그려야 되잖아」*).
**단순히 앞당길 수는 없다**: IP-Adapter 레퍼런스는 화면 **전역** 적용이라 다인물 장면을 오염시키고
(ADR `260822-111304`, 다인물 정차지 **47건 15%**), 골리앗이 정확히 그 2인 케이스다. 그리고 매체 교체(A)
뒤에는 「컷마다 같은 사람」을 보장하는 주체가 **SVG 선화 정본에서 생성 레퍼런스로** 옮겨가야 하는데
그 처분이 ADR `260824-002411`에 **미결**로 남아 있다(현재 `sketches/cast/`에는 다윗 머리 1건뿐이고
골리앗 정본은 없다). ⇒ **선행 순서: 설정화의 형태 결정 → 다인물 조건화 → D_conti 재측정.**
따라서 **원가표는 D_model 91선 기준으로 닫는다**(계획 S3의 음성 결과 분기): 회귀식
`줄(D) = 14.9 + 1.939·D`로 D=91은 장면당 **191.3줄**, 현재 평균 35.1줄 대비 **순증 156.2줄/장면**,
**291장면 = 45,468줄**이다(위 원가표 행들은 분모 293장면 = 45,781줄을 쓴다 — 291은 「22선 미만 장면」,
293은 「D_model 미달 장면」이라 분모가 다르다. 같은 표 안에서 섞어 인용하지 말 것).
이 숫자를 이미 만족하는 실존 사례는 `frontend/src/sketches/davidUnitedKingdom.jsx:GoliathScene`
(218선, 이번 측정의 대상 장면)과 `frontend/src/sketches/gospelOfJesus.jsx:TransfigurationScene`(192선)이다.

**이 값을 인용할 때 반드시 함께 인용할 한계 셋.** ① **감선 축만 쟀다** — 218선을 깎아 만든 57선과
10선에 구조를 더한 57선은 다른 그림일 수 있고(전자는 디테일이 빠진 것, 후자는 구조만 있는 것),
**증선 축은 재지 않았다.** ② **장면 1건의 결과다** — 2인 구도·쓰러지는 자세라는 이 장면 고유 조건이
결과를 지배했을 가능성이 크다(다윗은 같은 조건에서 성공했다). ③ **네거티브 프롬프트에
`stick figure, crude drawing`이 들어 있다**(task#305 동결 설정 승계) — 막대 형상의 육화를 억제했을
가능성이 남으며 이 축은 재지 않았다. **따라서 「D_model 91선이면 된다」는 이 측정이 확인한 명제가
아니다** — 218선(D_model의 2.4배)에서도 골리앗은 실패했다. 91은 **측정된 하한이 아니라 물려받은
기준점**이고, 표를 닫기 위한 값이다.

**이 전환이 남긴 큰 구멍은 게이트다.** `validate_scene_sketch_detail.py` B1~B12가 전부 SVG stroke를
세는데, 화면 자산이 래스터가 되면 드로인 타이밍 축(B4·B5·B6·B9)은 대상을 잃고 형태 축은 콘티에만 남는다.
그리고 **「이 그림에 골리앗이 있는가」**를 물을 수단이 없다(로컬에 생성 모델은 있고 이해(VLM) 모델은
미설치) — 미결이며, ADR `260824-002411`이 별건 결정으로 표시했다.
→ [[장면 스케치]], [[조건 입력 적합성]], [[판독성]], [[장면 밀도]]

**장면당 두 자산이 짝으로 묶인다** — 선화(잉크 + 생성 조건 입력)와 채색층(픽셀). 어긋나면 화면에
찢어진 공개로 보이므로 파생값을 닫는 주체가 필요하다. 좌표계도 공유해야 한다: 조건 입력을 종횡비
무시로 늘려 만들면(S4의 `prep.py`) 축별 배율이 어긋나 장면마다 정렬을 역산해야 하고, 선화를 목표
해상도로 직접 래스터화하면 선화 좌표가 곧 채색층 좌표가 된다(실측: 대응 지표 39% → 56%, 조건 입력의
인물 4인이 4인으로 살아남았다).

**채색층은 종이색을 투명으로 가져야 한다.** 이 층은 붓질 마스크(저작 경로를 굵은 선으로 훑은 것)를
통해 드러나므로, 배경이 불투명하면 **붓이 선 밖으로 나간 자리까지 칠해지고** 성문·지면 주위에 종이색
얼룩이 남아 「선 안을 칠한 것」이 아니라 **「형광펜으로 선을 덧그은 것」**으로 읽힌다. 종이보다 밝은
화소는 그대로 두면 **구멍**으로 읽힌다 — 칠이 아니라 결손이므로 투명이 맞다(2026-08-23 실측:
얼룩·구멍이 알파 도입으로 소거). 대가는 바이트다: 알파 채널의 엔트로피 때문에 같은 장면이
12.7KB(RGB) → 50.2KB(RGBA q88, 알파 8단계 양자화 + 투명 구간 RGB 평탄화 후)로 4배가 된다.
→ [[장면 스케치]], [[조건 입력 적합성]], [[장면 밀도]], [[설정화]]

**2026-08-26 — 콘티는 장면 스케치를 재사용하지 않고 별도로 저작한다**(ADR `260826-082626`,
task#318 S2·S3). 지금까지 콘티는 앱의 [[장면 스케치]](`GoliathScene`)를 그대로 조건 입력으로
재사용했는데, S2가 그 결과를 원자료로 대조하니 서사 기호 6종·그려진 이목구비 2건·형체 불명 지물
2건 총 10개 항목이 조건 입력을 거쳐 최종 생성물에 낙서·강제 표정·정체불명 사물로 그대로 실렸다
(`scripts/canon/notes/PROCESS.md` §7) — 이 절이 위에서 규정한 「콘티는 구도만 나른다」에 맞는
항목이 하나도 없었다. 그래서 콘티를 `scripts/canon/conti/`에 자립 HTML+SVG로 별도 저작한다(레이어
`bg`·`david`·`goliath` 분리, `render_conti.py`가 playwright로 렌더 — 앱을 경유하고 투어 캡션으로
정차지를 찾는 `render_scene.py`는 앱 변경 없이 쓸 수 없었다).

## 인물 정본 (Character Sheet)

[[설정화]]의 한 갈래 — 인물별 **머리 윤곽 + 머리카락 + 수염 + 머리쓰개**를 컴포넌트로 정본화한 것
(`frontend/src/sketches/cast/`). **이목구비는 슬롯으로 비우고 장면별로 저작한다**: 렌더 배율
약 3.7px/단위에서 머리 지름 30px일 때 정체성을 나르는 것은 실루엣이고, 이목구비는 표정 — 즉 서사다.
이 분해로 머리 **방향** 조합 폭발이 사라진다(실루엣은 방향에 둔감하다).

목적은 **정체성**이다 — 다윗은 어느 장면에서나 같은 사람이어야 하므로 **재사용이 의무**이고, 검증기가
강제한다(B12: 인물 이름표가 있고 그 인물의 정본이 존재하면 그 장면은 정본을 써야 한다). 정본은
**인물이지 이름이 아니다** — `아브람`/`아브라함`은 정본 하나에 이름표 둘이고, 정본 파일이 자기 별칭을
선언한다. **임계 규칙**: 3장면 이상 등장하는 인물에게 정본을 만든다(2회 이하는 컴포넌트 도입 비용이
손저작과 비슷해 순이득이 없다). **명단은 확정하지 않는다** — 각 파트가 재작도하며 정한다.
인물은 거의 단일 투어에 갇혀 있으므로(예외: 베드로·사무엘) 이 자산은 **투어 내** 일관성을 담당한다.

**정본의 크기는 실루엣이 아니라 슬롯이 요구하는 최소 해상도가 정한다**(task#307 파일럿 실측).
머리 반지름을 2.6~2.8로 줄이면 장면이 그 위에 얹는 이목구비가 먹덩이가 되므로 「기존 도형 크기를
유지하며 머리만 교체」는 성립하지 않는다 — 실제 하한은 반지름 4단위다. 같은 이유로 얇은 텍스처
선(굵기 1.1~1.4)은 실루엣이 못 된다(격리하면 뭉쳐 「눈썹 두 개」로 읽히고 원경 ×0.45에서 소실된다) —
실루엣은 구조 선(≥2.0)이 진다. `stroke-width`는 `scale`로 곱하지 않는다(검증기 `_SW`가
`sw(<리터럴>)`만 읽어 구조 선이 조용히 미분류된다).

⚠ **파일럿(task#307)은 기계 축 전부를 성립시켰으나 사람 판정이 「전면 재설계」였다** — 이 항목의
설계(강제 컴포넌트·이목구비 슬롯·B12)는 폐기도 확정도 아닌 **재설계 그릴링의 입력**으로 재개된
상태다(ADR `260823-190821` 2026-08-23 개정). 작동하는 구현물은 남아 있다.

**2026-08-24 재설계 확정 — 정본은 2층이고, 정체성은 두 축이다**(ADR `260824-075708`. 위 ⚠의 재설계
그릴링이 여기서 닫힌다).

**2층.** 매체 교체(ADR `260824-002411`)로 화면 자산이 생성 래스터가 되면서 「같은 사람」을 보장하던
컴포넌트 재사용이 작동하지 않는다 — 생성 모델에는 기억이 없다(실측: 레퍼런스 없이 같은 콘티로 낸
45장에서 다윗이 칸마다 다른 아이였다, task#308).
- **1층 = SVG 실루엣**(현행 `sketches/cast/`) — 머리 윤곽·머리카락·수염·머리쓰개. 이목구비는 슬롯으로
  비운다(위 결정 유지). [[콘티]]에서 「누구인지」를 **선으로** 지시한다.
- **2층 = 동결 얼굴 래스터** — 1층을 조건으로 후보를 뽑아 **사람이 한 번 고르고 동결한 PNG 1장**.
  생성 시 IP-Adapter 레퍼런스로 물린다. 1층은 원 하나 + 실루엣이라 그것만으로는 모델이 얼굴을
  **지어내므로**, 「정본에서 파생」이 성립하려면 파생 결과를 고르고 못 박는 단계가 있어야 한다.

**두 축.** 지금까지 이 항목이 적어 온 정체성은 **일관성**(다윗은 모든 컷에서 같은 사람) 한 축이었다.
사용자 판정(2026-08-24 *「모든 인물이 다르게 그려지도록」*)이 **구별성**(다윗 ≠ 요셉 ≠ 베드로)을
두 번째 축으로 세웠다. 구별성은 2단으로 보증한다 — **① 구별 조합표**(머리카락 4 × 수염 4 × 머리쓰개 5 ×
나이대 4 × 성별 2 = 640조합에서 인물마다 겹치지 않는 조합을 배정, 「중복 0」은 기계가 센다) ·
**② 쌍거리 게이트**(동결 얼굴 전수의 CLIP 이미지 임베딩 쌍 유사도가 임계를 넘으면 통과 불가.
**임계값은 얼굴 크롭 전수로 보정해 정하며 지어내지 않는다**).

**⚠ 위의 「3장면 이상 등장하는 인물에게 정본을 만든다」 임계 규칙은 폐기됐다.** 그 임계의 근거는
SVG 저작 경제였는데, 2층에서 정본은 **구별성의 근거**이기도 하다 — 한 번만 등장하는 인물이 다윗과
똑같이 생기면 그것도 결함이고 등장 횟수와 무관하다. **대상은 이름표에 등장하는 인물 전원**이며
(예수 포함 — 예외 없음, ADR-0025 2026-08-24 개정), **이름표가 아니라 인물로 센다**(별칭 병합
`아브람`=`아브라함` · 동명이인 분리 `요한`≠`세례 요한`). 실측(2026-08-24): 이름표 74개·등장 195 ·
2회 이상 40개(83%) · 3회 이상 27개(69%). **얼굴 선택은 2회 이상 등장 인물을 사람이 고르고 1회 등장은
게이트가 자동 선택하되, 게이트는 전원에 동일 적용한다.**
**2026-08-24 파일럿 확인 (task#314) — 2층이 실제로 정체성을 날랐고, 층이 하나 더 붙었다.**

수직 파일럿이 `GoliathScene` 한 건으로 「장면 확인 → 정본 저작 → 후보 생성 → 사람 확인」을 관통했다.
1층 SVG 실루엣만을 조건으로 뽑은 후보에서 **다윗 4/4가 곱슬머리·마른 얼굴의 열두 살 소년**,
**골리앗 4/4가 찌푸린 눈썹·노려보는 눈의 험악한 투구 거인**으로 나왔다 — 5축이 후보에 나타난다.
「정본에서 파생」이 주장이 아니라 관측이 됐다(ADR `260824-075708` 2026-08-24 개정).

**단, 5축은 인물을 식별하지 구술하지 않는다.** 5축만으로 파생한 골리앗은 「투구 쓴, 수염 없는, 성인,
남성」 — 아무 병사다. 「거인」도 「위협」도 담을 축이 없다. 그래서 **`BRIEF`(자유 문장 묘사)가 5축과
나란한 별개 층**으로 선다(ADR `260824-191251`). 둘은 목적도 검증도 다르다 — **5축은 구별성을 지고
기계가 센다**(640조합 중복 0, `scripts/check_cast_axes.py`), **`BRIEF`는 묘사를 지고 사람이 후보를
보고 판정한다**. `BRIEF`를 6번째 축으로 넣지 않은 이유는 자유 문장이 조합표의 「중복 0」 셈을 깨기
때문이다. 드리프트 방어는 **출처 고정** 하나뿐이다 — `BRIEF`는 손으로 짓지 않고 **이미 승인된 장면
저작의 주석에서 파생**한다(골리앗의 「얼굴 — 위협」).

**배경은 이 구조를 받지 않는다.** [[설정화]]가 앞단계로 열거한 「캐릭터 설정과 배경 설정」 둘 중
배경은 **정본 자산이 되지 않는다** — 인물의 1회성이 2.9%(34명 중 1명)인데 장소는 **60.3%**(121곳 중
73곳)로 재사용 곡선이 20배 다르다. 배경은 장면 자신의 인라인 SVG + 프롬프트 어휘가 진다

**후보를 뽑는 값은 정본에 없다.** 조건 입력 강도·굵기·프롬프트 파생 규칙은 정본이 아니라 파이프라인의
값이고, 정본에서 **승계하지 않는다**(ADR `260824-191250`) — → [[조건 입력 적합성]].

| `ip_adapter_scale` | 15세 자기/교차 | 62세 자기/교차 | `sim(15,62)` |

| **0.3 (확정값)** | **0.9621** / 0.4643 | **0.7002** / 0.5268 | **0.7060** |

## 전신 표본 (Figure Sample)

[[인물 정본]] 2층의 2026-08-26 형태 — 인물 한 명의 **중립 정면 단독 전신** 래스터 1장을, 후보를 뽑아
**사람이 고르고 동결한** 것. 생성 시 IP-Adapter 레퍼런스로 물린다. 동결 얼굴 래스터를 대체한다.

**단독 포즈인 것이 요건이다.** 다포즈 캐릭터 시트를 레퍼런스로 물리면 **배치까지 전이돼** 산출물에
인물이 여럿 생긴다(실측: 화풍 시트를 낮은 ControlNet 강도로 물렸을 때 인물이 3명이 됐다). 그래서
표본은 시트가 아니다 — 시트는 [[화풍 도달]]의 양성 기준이고, 표본은 [[정본 전이]]의 기준이다.

**무엇에서 파생되는가**: 5축(`sketches/cast/*.jsx`의 `AXES`) + `BRIEF` + `data/person_events`의 나이.
손으로 문구를 적지 않는다 — 적으면 데이터와 드리프트한다. 화풍은 프롬프트의 형용사가 아니라
레퍼런스로 얻는다.

**동작은 표본이 지지 않는다.** 표본이 정체성을 지므로 [[콘티]]와 프롬프트가 예산을 **동작**에 쓸 수
있다 — 그것이 이 분업의 목적이다.

**⚠ 그러나 그것은 규범이고, 파이프라인은 2026-08-30 현재 그것을 어긴다.** 표본 프롬프트가
`standing alone, facing forward, head to toe`로 **자세를 명시**하고([[생성 파라미터]]가 아니라
`derive_prompts.sample_prompt`의 문구다), [[정본 전이]]를 재는 축이 크롭 **전체**의 CLIP 임베딩을
표본 전체와 비교하므로 **자세 복제도 전이로 센다**. 그래서 그 축을 세게 통과시킬수록 산출물의
자세가 콘티에서 멀어진다 — task#320이 축을 통과시키려 표본 강도를 0.7 → 0.9로 올리자 다윗의
감아올린 팔이 표본의 차렷 자세로 내려왔다(승인본 s11의 팔 상관 +.0401, 배경만 음성이 +.0039).
**규범을 지키려면 축이 정체성 영역만 재야 한다** — 자세를 재는 일은 [[조건 입력 적합성]]의 몫이다.
**그 분리는 2026-08-30(task#321) 실측으로 성립함이 확인됐다** — 머리 밴드로 양쪽을 똑같이 잘라
재파생하면 귀무 통과 0/12 · 사다리 단조 · 양성 6/6 · 여유 +0.1129로, 현행(임계 +0.0729)보다
오히려 마진이 크다. **그런데도 교체하지 않았다**: 임계가 귀무 최대에서 기계적으로 파생되므로
산식을 바꾸면 task#320 승인본의 통과 증거가 다른 자로 잰 값이 된다(ADR `260830-125824`).

## 정본 전이 (Canon Transfer)

동결된 [[인물 정본]]의 얼굴이 **실제 산출물에 얼마나 실리는가**. [[조건 입력 적합성]]이 「콘티가 구도
조건으로 잘 작동하는가」를 묻는다면, 이것은 「레퍼런스가 정체성을 실제로 날랐는가」를 묻는다.
_Avoid_: 정체성 유지, 얼굴 일관성 (둘 다 결과만 가리키고 「전이」의 정도·측정을 못 담는다)

**층에 따라 갈린다 — 이것이 이 용어가 필요한 이유다.** task#315 실측:

- **초상 층에서는 강하게 전이된다.** 두상 조건 입력 · `PERSON_CN = 0.3` · `ip_adapter_scale = 0.3`에서
  동결본과의 CLIP 유사도가 15세 **0.9621** · 62세 **0.7002**이고, 다른 인물 동결본과의 유사도(0.46~0.53)를
  크게 웃돈다. 나이를 프롬프트로 얹어도 전이가 유지된다(ADR `260824-075708` 2026-08-25 개정).
- **장면 합성 층에서는 전이가 검출되지 않는다.** 4조건 × 3시드 = 12장에서 **레퍼런스를 아예 안 태운
  조건조차** 「정본대로인가」를 3/3 통과했고, 마스크 유무도 갈리지 않았다. 마스크를 건 조건의 화풍
  시드 간 산포는 기준선보다 오히려 나빴다.

**「검출되지 않는다」는 「전이가 없다」가 아니다.** 쓴 지표(인물 영역 크롭의 CLIP 교차 유사도)에
분해능이 없었을 가능성이 크다 — 그 지표가 재는 「왼쪽 크롭이 골리앗보다 다윗을 닮았는가」는 ControlNet
기하와 프롬프트가 이미 보장한다. 음성 대조군이 통과한 판정은 결과가 아니라 무정보다
(ADR `260825-013557`). 원자료는 `.forge/reports/canon-pilot/judge-metrics.json`, 판정표는
`JUDGE-MACHINE.md`, 초상 층 재시험은 `SWEEP2P.md`(전부 git 미추적).

**그래서 이것이 74명 확대의 선결 조건이다.** 정본을 74장 만들어도 그 값이 화면에 실렸는지 알 방법이
없으면 원가를 검증 없이 지불하는 것이다.

**2026-08-25 정정(task#317 그릴링) — 막힌 곳은 「이 축을 재는 도구」가 아니었다.** 위 문단은 원인을
판정 도구로 지목했으나, 원자료를 되짚으니 **눈으로 봐도 전이가 안 됐고 화풍도 목표가 아니다.**
도구를 고쳐도 그림이 좋아지지 않는다. 미배제된 파이프라인 층 원인이 넷 있다
(ADR `260825-013641`이 요구하는 배제 순서를 아직 밟지 않았다):

- **ControlNet이 [[화풍 도달]]을 죽인다** — CN 없이 뽑은 그림은 목표 화풍이고 CN 경로는 창백하다.
  **강도로는 풀리지 않는다**(CN 0.5에서 이미 창백). 그리고 `raster-pilot/FINDINGS.md`가 이 드리프트를
  **미시험 후보로 적어 둔 채** 그 위에 파일럿 3건이 쌓였다. 미시험 처방: `control_guidance_end`
  (초기 스텝만 CN) · 2패스 img2img · 스타일 LoRA.
- **장면 프롬프트에 정체성 어휘가 없다** — 초상은 「boy of fifteen, lean-faced, curly hair」인데
  장면은 「a small shepherd boy」 한 마디다. IP-Adapter 혼자 나르게 두었고 「small」이 치비를 부른다.
- **인물이 작다** — 다윗 bbox 251×327(캔버스 1216×640), 얼굴 약 60px = 동결본 1024px의 **1/17**.
  이것이 원인이면 처방은 파이프라인이 아니라 **콘티 구도**이고 296장면 저작 규약이 바뀐다.
- **다인물 마스크가 헐겁다**(bbox라 배경을 품는다).

**⇒ 이 넷을 배제하기 전에는 「장면 층에서 전이가 없다」고 말할 수 없다.** 반대로 「검출 도구만 있으면
된다」고도 말할 수 없다.

## 화풍 도달 (Style Fidelity)

생성물이 **사용자가 지정한 목표 화풍의 그림인가.** [[조건 입력 적합성]]이 「콘티가 구도 조건으로 잘
작동하는가」를, [[정본 전이]]가 「레퍼런스가 정체성을 날랐는가」를 묻는다면, 이것은 세 번째 축이다 —
**구도가 맞고 정체성이 실려도 그림이 목표와 다른 물건일 수 있다.**
_Avoid_: 「화풍 일관성」(시드 간 균질성은 다른 축이다 — 균질하게 틀릴 수 있다)

**정답지가 있고, 지어내지 않는다.** 목표는 사용자가 2026-08-24에 제시한 생성 이미지들과
`sheet-s200~203`이며(ADR `260824-002411`이 매체 교체의 근거로 삼은 바로 그 그림들), 이것들이 판정의
양성 기준이다.

**재는 자를 고르는 방법이 이 용어의 핵심이다.** 육안 소견은 「창백하다」이고 거기서 자연스럽게 나오는
지표는 채도인데, **채도 평균은 정답지와 현행의 구간이 겹쳐 아무것도 갈라내지 못한다**(정답지
0.201~0.259 ↔ 현행 0.105~0.217). 실제로 갈라내는 것은 **어두운 화소 비율**(`v<0.55`)로, 정답지
0.161~0.233 ↔ 현행 0.003~0.010으로 **17~75배** 벌어진다. 즉 결함의 정체는 채도가 아니라
**잉크·대비의 부재**다. 지표는 고르기 전에 정답지와 현행 양쪽에 걸어 분리도를 잰다
(ADR `260825-013557` 2026-08-25 개정 따름 정리 1).

**적용 범위는 장면류다.** 동결 정본(얼굴 클로즈업)의 같은 지표는 0.006으로 실패해야 할 현행 장면과
같다 — 초상은 원래 어두운 화소가 적다. 이 자를 초상 판정에 쓰지 않는다(같은 개정 따름 정리 3).

**기계는 후보를 거를 뿐 합격을 주지 않는다.** 최종 판정은 사람이며, task#307이 기계 전 축을 통과하고
사람 판정 「전면 재설계」로 죽은 것이 그 역할 분담의 근거다.

**이 자가 재는 것은 화풍의 「계열」이지 계열 안의 세부가 아니다** (2026-08-29 실측, `notes/ZIMAGE.md`
§9-14·§9-20). 같은 내용·같은 CN으로 화풍 블록만 바꿔 뽑은 네 계열(유화·잉크만화·3D렌더·플랫벡터)을
전역 `ink`가 **전부 거른다**(정답지 .1024~.2213 ↔ 음성 .2567~1.0). 그러므로 「축 A가 화풍 종류를
못 잰다」는 진단은 **과했다** — 못 재는 것은 목표 계열 **안에서** 갑주가 판금인지 어린갑인지이고,
그것은 화풍이 아니라 **의상**이다. 이 혼동이 다섯 라운드를 지표 설계에 쓰게 했다.

**하한이 요구하는 것은 「많이 그려라」가 아니라 「진하게 그려라」다.** 성긴 장면에 부당한 요구가
아닌지 재 보니(§9-20) 우리 장면의 **밀도는 정답지 구간 한가운데**(.41~.54 ↔ .26~.71)였고, 낮은
`ink`의 정체는 **그린 영역 안이 옅다**는 것이었다(.174~.303 ↔ 정답지 .275~.638). 밀도로 정규화하면
오히려 **화풍 분리가 깨진다**(정답지 상한이 음성 하한을 넘는다) — 정규화가 교란과 함께 신호도 지운다.

**의상은 별도 축이고, 그 축도 종류는 못 잰다.** 축 F(갑주 착용 여부)는 몸통 밴드에 대립쌍을 걸어
**착용/부재**를 가른다(양성 2/2 · 음성 0/3). 그러나 **비늘 vs 판금**은 텍스트 대립쌍·이미지 원형·
프롬프트 라벨 대조군 **세 기제가 전부 실패**했다(§9-15). CLIP 대립쌍은 존재/부재에 강하고 한 종류
안의 세부에 무력하다 — 그러므로 축 F의 통과를 「의상이 정본과 맞다」로 읽으면 안 된다.

## 생성 파라미터 (Generation Parameter)

[[인물 정본]]의 후보와 장면을 뽑을 때 파이프라인이 쓰는 값 — 조건 입력 굵기·2값화 임계 · ControlNet
강도 · IP-Adapter 강도 · 모델 ID · 스텝 · guidance · 시드 · 캔버스 크기.
_Avoid_: 「파이프라인 정본」·「생성 정본」 (이 글로서리에서 **정본은 사람이 동결한 얼굴**을 뜻한다.
생성 파라미터는 정본이 아니고, 정본에서 **승계하지도 않는다** — ADR `260824-191250`)

**조건의 종류에 종속된다.** 하나의 평면 집합이 아니라 **조건 종류별로 갈린 묶음**이다 — 두상 조건과
장면 콘티는 같은 이름의 값(ControlNet 강도)이 서로 다른 수(0.3 ↔ 0.8)를 갖고, 바꿔 쓰면 두상이 빈
타원이 된다. 평면 네임스페이스는 그 오용을 초대한다.

**선언은 한 곳이고 나머지는 파생한다 — 이제 기계가 강제한다.** 값이 여러 파일에 복사되면 한 곳만
고쳤을 때 나머지가 조용히 옛 값으로 돈다(에러 없이 그림만 달라지는 결함 클래스, ADR `260823-221839`).
task#316 착수 시점 실측으로 13개 스크립트 중 규율을 지킨 값은 셋뿐이었고 나머지는 최대 6중 복사였다.
**정본은 `scripts/canon/params.py`** 하나이고, `backend/scripts/validate_canon_pipeline.py`가 정본 밖
재선언을 배포 차단 강도로 막는다. **파생은 언제나 정본을 읽는다** — 그 값을 쓰는 다른 소비자의 소스를
긁는 파생은 정본이 생기는 순간 죽는다(ADR `260823-221839` 따름 정리 4).

**그 강제에는 경계가 있다 — 초록을 「드리프트 없음」으로 읽지 않는다.** 게이트는 정본이 선언한
**이름**의 재선언과, 정본이 선언한 **모델 ID 리터럴**의 재등장만 본다(ADR `260825-074924`).
정본이 안 쓰는 이름으로 같은 수를 새로 적는 것은 잡지 못한다 — 수치까지 값으로 보면 오탐이 확실해
의도적으로 좁게 뒀다. 그리고 이름 축을 켠 대가로 **정본의 키 이름은 그 디렉터리의 전역 예약어**가
된다(정본 쪽이 `BASE`가 아니라 `SDXL_BASE`인 이유가 그 충돌이다).

**저작 도구이지 앱이 아니다.** 런타임 의존이 앱과 다르고(torch·diffusers ↔ fastapi·neo4j) 배포
이미지에 들어가지 않는다 — ADR `260825-065028`.

**판정의 파생원을 겸하는 값이 있다 — `REGIONS`.** 구역 상자는 생성 쪽에서 「어디에 얼마나 크게
세울 것인가」를 정하지만, `judge_scene.c3_paste_seam`이 **같은 상자를 그대로 읽어**
`_edge_seam(cur, prev, box(region))`으로 이음매를 잰다. 그래서 상자를 옮기면 그림만 바뀌는 것이
아니라 **C3가 무엇을 재는지가 함께 바뀐다** — [[지표를 정의하는 상수]]의 성격을 겸한다.
2026-09-02 실측: 골리앗 구역 하단을 0.95 → 1.00으로 내리면 하단선(639)이 `_edge_seam`의 가장자리
가드(`line < 636`)에 걸려 **그 변이 판정에서 통째로 빠지고**, 최악값이 0.511(하단) → 0.333(우측)으로
내려가 C3가 「통과」한다. `judge_scene.py`를 한 줄도 안 고쳤는데 임계를 푼 것과 같은 효과다.
그러므로 `REGIONS` 변경은 ADR `260830-125824`(게이트의 파생원 교체는 사람의 결정)의 적용 대상이다.

## 지표를 정의하는 상수 (Metric-defining Constant)

판정 지표의 **산식 자체**를 정의하는 값 — 「무엇을 재는가」를 정한다. 통과선인 **임계가 아니고**,
파이프라인이 그림을 뽑을 때 쓰는 [[생성 파라미터]]도 아니다.
_Avoid_: 「임계」·「매직 넘버」·「튜닝 값」

예: `judge_style.DARK_CUT`(무엇을 「잉크」로 셀 것인가) · `judge_s1.ARM_Y_ABS`(팔 영역의 경계) ·
축 G의 `w_min`·`reach`(무엇을 「사지의 두께」로 볼 것인가).

**왜 임계와 갈라 부르는가.** 이 파이프라인의 제1 규율은 **「미달은 임계로 풀지 않는다」**이다 —
임계는 음성·양성 대조군에서 기계적으로 파생하고 손으로 못 고친다(ADR `260823-221839` ·
`260825-013557`). 그 규율을 이름 없이 두면 두 방향으로 샌다: 산식을 설계하는 데 필요한 수까지
「손대면 안 되는 값」으로 굳어 **개선 자체가 막히거나**, 반대로 임계 조정이 「지표 상수 조정」으로
**위장**된다. 구분선은 하나다 — **그 값을 바꾸면 「무엇을 재는가」가 바뀌는가(지표 상수), 아니면
「어디서 자르는가」만 바뀌는가(임계).**

**지표 상수도 근거를 지고 명시한다.** 손으로 고른 수가 아니라 **저작 원본이나 물리적 기제에서
파생**하고 그 파생을 적는다 — 축 G의 `w_min = r − 2`는 저작 획 두께 7px에서 엣지 검출이 경계
안쪽 1px씩에 놓이는 것을 뺀 값이고(그래서 콘티 자신의 실측 폭이 5~7이다), `reach = 4r`도 같은
획 두께에서 나온다. 근거 없는 수는 지표 상수가 아니라 그냥 매직 넘버다.

**선언 위치도 [[생성 파라미터]]와 다르다.** `params.py`가 아니라 **그 지표를 쓰는 판정 모듈 안**에
산다 — 생성이 읽는 값이 아니기 때문이다(`judge_style.py`의 선례).

**그 선언 위치 규칙에는 예외가 하나 있다 — `REGIONS`는 생성 쪽(`gen_scripture_scene.py`)에
살면서 판정의 파생원을 겸한다.** C3가 그 상자를 읽으므로 상자를 옮기면 「무엇을 재는가」가 바뀐다
(실측은 [[생성 파라미터]]에 적었다). 선언 위치로 성격을 판별할 수 없는 값이 있다는 뜻이고,
구분선은 여전히 하나다 — **바꿨을 때 「무엇을 재는가」가 바뀌는가.**

## 고정한 순간 (Fixed Moment)

한 장면이 담는 **성경 본문의 한 시점**. 여러 절에 걸친 사건에서 화면이 담을 수 있는 순간은 하나뿐이라
명세가 먼저 고르며(`notes/SCENE-1SAM17.md` §5), **화면 요소의 요구는 절이 아니라 그 순간에서 파생한다.**
절별 표는 요구가 아니라 **재료**다.
_Avoid_: 「본문에 있는 것」 (어느 절에 있느냐를 말하지 않아 요구가 서로 다른 순간의 합집합으로 쌓인다)

**한 번 물렸다.** 삼상17 명세는 §3에서 다윗의 지물을 17:40(「손에 막대기를 가지고 … 손에 물매를
가지고」)에서 뽑고 §5에서 순간을 17:48-49로 고정했는데, §0의 체크리스트가 §3의 목록을 그대로 받아
둘을 합쳤다. 그런데 17:49는 「**손을 주머니에 넣어** 돌을 취하여 물매로 던져」라 그 순간 두 손이 다
찼다 — 막대기를 들 손이 없다. 모델이 「손에 지물을 하나만 쥔다」는 실측(다섯 문구 × 네 시드)은
그 물리와 **일치**했다. 요구가 틀렸는데 그림을 더 태워 얻으려던 것이다(ADR `260902-170558`).

**여기서의 「지물」은 [[지물 어휘]]의 그것이 아니다.** 저 항목은 [[설정화]]의 갈래로 반복 배경·소품의
**참고 도상**(제단·성문·장막)을 말한다. 이 항목이 말하는 것은 **그 순간 인물이 손에 들고 있는 것**
(막대기·물매·창·방패)이고, 판정 대상도 도상 일관성이 아니라 **본문 충실**이다.

**파생 규율**: 순간에서 요구를 파생하면 **뺀 요구의 근거가 화면에 보여야** 한다. 「막대기가 없는 것은
두 손이 이미 찼기 때문」이라면 그 찬 손이 그려져야 하고, 안 보이면 다음 사람은 「본문에 있는데 왜
안 그렸나」를 다시 묻는다.

**그러나 그 규율은 실측에서 한 번 꺾였다**(2026-09-02, task 327). 17:49의 「손을 주머니에 넣어」를
넣는 문구 셋(물매를 앞에 둠 · 목적 명시 · 주머니를 앞에 둠)이 **전부 물매를 죽였다** — 그릇(bag)을
그리려면 모델이 손 하나를 비워야 하고, 「한 손에 지물 하나」와 겹쳐 앞의 지물이 죽는다. 물매는
17:40·17:49 둘 다에 있는 필수 지물이므로 **물매를 지키는 쪽이 이긴다.** 그래서 규율은 **이상으로
남고, 못 보일 때 근거는 문서가 진다**(`notes/SCENE-1SAM17.md` §19). 문구로 더 시도하지 말 것 —
task 325(막대기) · S9(허공의 지물) · task 327(주머니에 넣은 손)이 **같은 제약의 세 얼굴**이다.

**순간을 옮겼다**(2026-09-03, task 329 그릴링). 17:48-49 전반(달리며 물매를 쥠)에서 **17:49 후반(물매로 던지는
순간)** 으로 — 사용자가 v39를 보고 「물맷돌 던지는 모습이 아니다」로 판정했다. 원칙(순간이 요구를 판다)은 그대로고
값만 바뀐다: 던지는 순간에도 두 손은 물매(휘두르는 손)와 주머니 쪽에 있어 **막대기는 여전히 요구가 아니다**
(ADR `260903-062732`). 앞 문단의 「달림」은 요구에서 빠지고 「투척 자세·손에서 시작하는 끈」이 들어온다.

**그리고 되돌렸다**(2026-09-03, task 329 실행). 판 방식에서도 투척 자세는 문구 3종 × 시드 4 = 12장에서 0장 —
모델의 소년 prior에 「던지는 물매」가 없다. 062732의 되돌리기 조건이 충족돼 ADR `260903-154254`가 순간을
**17:48-49 전반(달리며 물매를 쥠)** 으로 되돌렸다. 같은 실측에서 **주머니도 요구에서 빠졌다**: 손의 물매와
주머니는 24장 중 한 그림에 함께 나온 적이 없다(모델은 인물에 지물 하나만 붙인다 — task 325의 재현). 순간의
요구는 「소년 · 시대 복식 · 손에 쥔 물매(끈이 손에서 시작) · 달림」이다. 실측표는 SCENE-1SAM17 §21. → [[한 인물 한 지물]]

→ [[지물 어휘]], [[단계 기여]]


## 장면 명세 (Scene Spec)

한 정차지의 그림이 담을 것을 **본문에서 파생해 데이터로 적은 것** — 절 인용 · [[고정한 순간]] · 배경 요소 · 인물([[인물 정본]]
id · 자세 · 지물 **하나** · 방향 · 구역) · 군중 · 구역 상자 · 배경 단계 순서. 요소마다 **출처 절**을 달고 본문 밖은 「본문 밖 ·
누가 정함」을 명시한다. **한국어 명세가 정본이고 영문 프롬프트는 파생물**이다 — 손으로 프롬프트를 쓰지 않는다. 파일은
`scripts/canon/scenes/<정차지-id>.json` — 삼상17이 첫 명세(`authored-david-goliath-gath.json`, task 330: 산문 §1~§5를 옮겨 적고 v41과 픽셀 동일로
회귀)이고, 생성기와 판정자가 **같은 파일**을 읽는다(ADR `260904-070504`). 파생 규칙은 `notes/PROMPTING.md` 15.
_Avoid_: 「프롬프트」 (파생물을 정본으로 부르면 규칙 수정이 문구 수정으로 새고, 근거 절이 사라진다)

→ [[고정한 순간]], [[한 인물 한 지물]], [[판 합성]], [[구절 근거 원칙]]


## 한 인물 한 지물 (One Prop per Figure)

이 생성 스택(Z-Image-Turbo, 77토큰 프롬프트)의 모델은 **인물 하나에 지물을 하나만 붙인다** — 문구가 둘을
요구하면 어느 쪽을 앞에 두든 하나가 죽고, 남은 하나가 다른 것으로 새기도 한다. 세 작업에서 같은 벽을 만났다:
task 325 막대기↔물매(다섯 문구 × 네 시드), task 327 주머니에 넣은 손↔물매, task 329 물매↔주머니(문구 3종 ×
시드 4 = 12장, 누적 24장에서 동시 출현 0). 그래서 [[고정한 순간]]의 요구를 쓸 때는 **인물마다 지물 하나를
고르는 것이 요구 설계의 일부**다 — 본문에 지물이 여럿이어도(17:40 막대기·주머니·물매) 그 순간의 손에 무엇이
있는지로 하나를 정하고 나머지는 요구에서 뺀다(다윗은 물매). 「어휘를 더 넣으면 된다」는 가정은 세 번 틀렸다.
[[판 합성]]으로 인물이 지형과 싸우지 않게 해도 이 제약은 그대로다 — 인페인팅의 문제가 아니라 모델의 것이다.
→ [[고정한 순간]], [[판 합성]]

## 단계 분할 (Stage Split)

한 [[장면 명세]]를 **생성 단계의 순서**로 나눈 것 — 단계마다 종류(배경 전체·구역·능선·인물 판·다듬기)·구역 상자·출처
절이 붙고, 영문 프롬프트는 단계마다 **파생**된다. 사람이 승인하는 사다리(본문 → 장면 서술 → 단계 분할 → [[단계 시도]] →
[[장면 완료]])의 세 번째 걸음이다.
_Avoid_: 「프롬프트 나누기」 (나누는 것은 프롬프트가 아니라 단계다 — 프롬프트는 단계의 파생물이고, 명세를 프롬프트라
부르지 않는 규율은 [[장면 명세]]와 같다)
→ [[장면 명세]], [[단계 시도]]


## 단계 시도 (Stage Attempt)

한 단계를 **한 번 생성한 결과** — 시드·문구·구역·앞 단계의 승인본이 입력으로 고정돼 같은 입력이면 재현된다. 사람이 한 단계의
시도들 중 하나를 골라 승인하면 그것이 그 단계의 **승인본**이 되고 뒤 단계의 입력이 된다. **승인은 사람만 한다** — 기계
판정 수치는 시도 옆에 붙는 참고값이지 승인이 아니다(4/7에서 기계 판정을 통과한 장면이 육안으로는 셋이 같은 그림이었다).

**의존 규칙.** 배경 사슬(전체 → 구역 → 능선)은 **순차 의존**이라 앞 단계의 승인본이 바뀌면 뒤는 [[재검토]]로 내려간다.
인물 판은 민 종이에 따로 그리므로([[판 합성]]) 배경과 **독립**이다 — 배경을 바꿔도 승인된 판은 살고 합성만 재검토된다.
장면 서술이나 단계 분할을 고치면 그 아래 시도 전부가 재검토다(첫 판은 예외 없이 단순하게, 아까운 재시도가 실측되면 좁힌다).
_Avoid_: 「후보」 (한 시도가 여러 장을 낼 수 있어 장 단위와 시도 단위가 섞인다), 「버전」 (장면 라벨 vNN과 충돌)
→ [[단계 분할]], [[재검토]], [[장면 완료]], [[판 합성]]


## 재검토 (Stale)

승인된 [[단계 시도]]의 **입력이 바뀌어**(앞 단계 승인본 · 명세 필드) 승인 효력이 멎은 상태. 시도 이력과 그림은 남고, 사람이
다시 보고 그대로 확인하거나 재시도한다 — 그대로 확인은 생성 없이 한 번 누르는 일이다.
_Avoid_: 「무효」 (지운다는 뜻으로 읽힌다 — 승인은 취소되는 것이 아니라 다시 볼 대상이 될 뿐), 「다시 볼 것」
→ [[단계 시도]]


## 장면 완료 (Scene Done)

모든 단계에 [[재검토]] 아닌 승인본이 있고 **최종 합성을 사람이 승인한** 상태. 완료된 장면은 승인본의 시드·문구가 전부 기록돼
있어 재현 명령이 산출물을 대신한다(산출물은 레포에 들어오지 않는다는 규약 그대로).
→ [[단계 시도]], [[장면 명세]], [[장면 고르기]]


## 장면 고르기 (Scene Pick)

한 장 생성 경로(Z-Image 한 장 + 정본 참조 편집)에서 사람이 **한 번 앉은 자리에서 한 장면의 완성 후보 여러 장을 보고, 장면 요소마다
쪼갠 문항(장면 뜻·배경·인물별 같은 사람·자세·지물·방향, 그 밖의 결함)에 「틀린 후보」를 표시한 뒤 마지막에 하나를 고르거나 「없음」을
답하는 일**. 요소 문항은 [[장면 명세]] 칸에서 뽑아 답이 곧 고칠 칸을 가리킨다. 후보는 기계가 사람 없이 미리 다 만들어 둔 바탕들이다. 정본 참조 편집은 고른 바탕 한 장에만
걸고, 편집본과 바탕을 한 화면에서 한 번 더 견줘 승인본을 정한다(ADR `261017-152627` 2026-10-19 개정). 고른 장이 그 장면의 승인본이고, 그 장에 남은 틀린 요소가 고칠 곳 목록이다. 단계 사다리([[단계 분할]]·[[단계 시도]])는 판 합성 경로의 승인이고, 이것은 그 경로를 쓰지 않는 장면의 승인이다.
_Avoid_: 「판정」 (판정은 처치 효과를 대조와 견주는 측정이다 — 고르기는 측정이 아니라 승인이다), 「검수」

**후보 화면 — 기계가 먼저 고르고 사람은 확인·뒤집는 고르기(2026-10-20, task 376에서 시험).** 기계 판정자가 모든 후보의 요소 문항에 먼저 답한 뒤,
사람에게는 장면마다 **기계 후보 한 장**(요소 문항을 기계 표시 없이 묻고 「쓸 만함/없음」)과, 같은 화면 아래 **나머지 후보의 작은 그림**(눌러 후보를 바꿈)을 보인다.
기계가 장면 뜻을 후보 전부 틀렸다고 본 장면은 **되돌림** 한 화면(「명세로 돌려보냄」 동의, 또는 살릴 후보를 누름)으로만 묻는다.
기계는 후보의 순서를 정할 뿐 승인하지 않는다 — 사람이 모든 후보를 볼 수 있고, 사람이 기계 후보를 바꾼 횟수가 거르기 성적이다.
문항마다 기계 표시를 미리 해 두고 전 문항을 다 묻는 **함께 판정 화면**과 다르다(그것은 손댈 칸을 줄이고, 이것은 화면 수를 줄인다).
_Avoid_: 「기계 승인」·「자동 통과」 (승인은 사람만 한다 — ADR `260905-104910`)
→ [[장면 완료]], [[인물 정본]]


## 판 합성 (Plate Composition)

인물을 장면 안에 인페인팅하지 않고 **민 종이에 단독으로 그린 뒤**(그 단독 그림이 「판」) **알파로
오려 캔버스에 얹는** 방식. 붙임 마스크가 사각형이 아니라 **실루엣**이므로 상자 잔상이 구조적으로
생기지 않고, 민 종이에서는 자세가 끌려갈 지형이 없다(ADR `260902-193724` · `notes/SCENE-1SAM17.md` §14).
_Avoid_: 「인물 인페인팅」 (장면 안에서 그리는 이전 방식을 가리켜, 상자 변 잔상과 비탈에 끌린 자세라는
두 결함을 함께 부른다)

**대가가 셋 붙는다.** ① 오려낸 인물은 배경과 닿은 적이 없어 떠 보이므로 **접지**를 따로 붙인다
(`_contact`). ② 얼굴 다듬기 단계는 판이 얼굴·방향을 이미 주므로 폐기했다. ③ **판 자신의 테두리가
새 변으로 들어온다** — 판 전체 bbox를 배율 기준으로 쓰면 얇은 끈이 인물을 축소시키고(task 326이
기준을 본체로 옮겨 갚음), 얇고 긴 지물이 그 변에 닿으면 그 자름이 곧 **이음매**다(C3의 정의는
`notes/SCENE-1SAM17.md` §15 — task 327에서
막대기를 빼자 0.2727 → 0.0).

**판 시대의 값은 상자 시대의 값과 이어 붙지 않는다** — v31 이전/이후를 같은 표에 놓을 때 경계를
명시한다.

→ [[단계 기여]], [[고정한 순간]]


## 최소 표본 가드 (Minimum-Sample Guard)

한 판정값이 **판정을 내릴 자격이 있는 표본 크기**를 정하는 문턱. 임계(통과선)와 다르다 — 임계는
「얼마여야 통과인가」, 가드는 「이 표본으로 그것을 잴 수 있는가」다. 가드에 못 미치면 그 자리는
통과도 실패도 아닌 **판정 없음**이다.
_Avoid_: 「임계를 낮춘다」 (가드를 고치는 일을 이렇게 부르면 「미달은 임계로 풀지 않는다」 규율에
걸리는 것처럼 읽힌다 — 가드는 무엇을 재는가에 속하고, 임계는 얼마여야 하는가에 속한다)

**가드는 임계의 기전과 같은 단위여야 한다.** 이음매 임계 0.40의 근거가 「한 **변의 대부분**에서
끊긴다」인데 가드가 **절대 픽셀 수**(n<20)였다 — 그래서 변의 6.6%짜리 표본이 판정을 받아 v38·v39가
걸렸다. 가드를 **변 길이의 비율**(1/5)로 옮긴 것이 ADR `260902-231339`.

→ [[지표를 정의하는 상수]], [[단계 기여]]


## 단계 기여 (Stage Contribution)

판정값이 **그 단계가 만든 것**을 재는가, 아니면 **그 자리에 원래 있던 것까지** 재는가. 단계별
인페인팅으로 그림을 쌓는 파이프라인에서 「구역 안의 값」은 언제나 **앞 단계들의 누적 + 이번 단계**라,
구역만 잘라 재는 자는 조용히 앞 단계를 세고 있다.
_Avoid_: 「구역 잉크」·「상자 값」 (그 이름이 바로 오해의 원인이다 — 무엇의 값인지 말하지 않는다)

**두 번 물렸다.** ① C2(군대)는 능선 띠의 절대 피복률을 재다가 지형 자체를 세었고, 「단계 직전/직후의
차이」로 바꾸고서야 정직해졌다(`notes/SCENE-1SAM17.md` §13). ② C4(화풍)의 `ink_david`는 다윗 구역의
총잉크인데, 그 구역에는 다윗이 그려지기 **전부터 지형이 0.0545** 있다 — 통과선 `c4_ink_min = 0.055`가
그 바닥보다 **0.0005 높을 뿐**이라, 지형이 조금만 촘촘해지면 **다윗이 통째로 사라져도 통과**한다
(2026-09-01 실측: v33 상자 0.1413·기여 0.0868 ↔ v35 상자 0.0851·기여 0.0307 — 겉보기 1.66배가
실제로는 2.8배).

**이것은 임계 문제가 아니라 산식 문제다.** [[지표를 정의하는 상수]]의 구분선을 그대로 적용하면,
「직전/직후의 차이로 바꾼다」는 **무엇을 재는가**를 바꾸는 일이라 지표 상수 수정이고, 통과선을 옮기는
일이 아니다. 그러므로 「미달은 임계로 풀지 않는다」는 규율에 걸리지 않는다 — 오히려 그 규율이
요구하는 방향이다.

**정답지 구간을 구역 값에 그대로 걸면 안 된다.** [[화풍 도달]]의 0.1024~0.2213은 **전역 잉크**에서
파생한 구간이다. 같은 수를 인물 구역에 걸면 지형 바닥이 얹힌 값과 비교하게 되어 자가 헐거워진다.
구역을 재려면 같은 방식으로 잰 **구역 대조군**이 있어야 하고, 없으면 프로젝트 안의 실측치끼리
비교한다(예: 「v33의 다윗 기여 0.0868 이상」).

→ [[지표를 정의하는 상수]], [[화풍 도달]], [[생성 파라미터]]


## 지물 어휘 (Prop Vocabulary)

[[설정화]]의 다른 갈래 — 반복 배경·지물(제단·성문·장막·나무·배·우물)의 **참고 도상**. 컴포넌트가
아니고 게이트도 없다. 저작자가 `#/cast`에서 보고 그린다.

목적이 정체성이 아니라 **도상 일관성**이기 때문이다 — 벧엘·모리아·갈멜산의 제단은 **다른 개체**이고,
「제단은 이렇게 생겼다」는 어휘를 공유할 뿐 같은 물건이 아니다. 변형이 위반이 아니라 정상이다.
컴포넌트로 만들지 않는 이유 셋: 개체가 다르므로 복붙하면 각 장면이 부정확해진다 · 변형을 prop으로
받으면 조건 분기가 생겨 검증기의 정적 인라인 전개(숫자 리터럴 prop만)를 깬다 · 이름표 같은 기계
신호가 없어 강제할 게이트가 애초에 없다. 지물은 여러 투어에 흩어져 나타나므로(제단 6모듈 · 성문 5 ·
장막 5) **투어 간** 일관성을 담당한다. → [[설정화]], [[인물 정본]]

## 동시 진행 선 수 (Concurrent Draw Count)

어느 한 순간에 **동시에 그려지고 있는** stroke의 수. [[붓질 단계]]가 "한 번에 나타나는 선"을 재는 것과 달리
이 축은 시간창을 잰다 — 모든 stroke는 `--dur-draw-scene` 동안 그려지므로, 단계 간격이 그보다 짧으면 앞 단계가
아직 그려지는 중에 다음 단계가 시작된다. **동시 진행 선 수 ≈ (dur-draw-scene ÷ 단계 간격) × 단계당 선 수.**

**이 축이 "그려지는 느낌"을 결정하고, 경계 B2(단계당 ≤3선)는 이 축을 지키려고 존재한다.** 그런데 B2는 단계당
개수만 재기 때문에 간격을 좁히는 경로로 우회된다. task#303 실측이 그 우회를 보여줬다 — B2를 3으로 지킨
3장면에서 500ms 창을 쓸어보니 **중앙값 11~15선**이 함께 그려지고 있었고, 드로인 구간의 95~97%가 4선을
초과했다. 설계 문서가 주장한 4.2선은 **겹치는 단계 개수만 세고 단계당 선 수를 곱하지 않은** 값이었다.

두 가지가 이 용어에 딸려 있다. 첫째, **이 축에는 아직 게이트가 없다** — 검증기는 B2(단계당)만 보고 시간창은
보지 않는다. 둘째, **순수 개수가 체감을 그대로 결정하지는 않는다** — 짧고 옅은 배경 획이 섞이면 11~15선이
동시에 그려져도 육안으로 "우수수"로 보이지 않았다(중간 프레임 실측). 그래서 상한을 숫자로 못 박기 전에
[[판독성]]처럼 사람 판정 기준선을 여러 장면에서 수집해야 한다.

경계 산식은 저작자가 유도하게 두지 말고 검증기가 계산해 출력하는 것이 옳다 — 이 축의 공식이 두 번 잘못
유도된 것이 근거다. → [[붓질 단계]], [[장면 밀도]], [[판독성]]

## 인물 연결 (Person Connections)

큐레이션 인물([[여정-journey]]을 가진 35인) 상세 시트에서 그 인물과 이어지는 **다른 큐레이션 인물**을 보여주는 두 축. 둘 다 **큐레이션 인물로 한정**되어 모든 항목이 여정으로 점프 가능하다 — 장소판 선례("이 곳을 지난 인물" = `/place/{id}/curated-persons`)의 인물판이다. 기존 SidePanel "이웃"의 가족 관계(부모·자녀·형제·배우자 등 직접 그래프 관계)와는 **다른 축**이며, 그것을 대체하지 않고 별도 섹션으로 얹는다.

- **함께 등장한 인물 (Co-participant)**: 같은 `Event`에 `HAS_PARTICIPANT`로 **함께 참여**한 인물. `Person`끼리는 직접 관계가 없고 `Event`를 경유한 2-hop 공동 등장이라(사건 → 참여자) 가족 관계와 의미가 다르다. **성경상 다른 큐레이션 인물과 같은 사건에 등장하는지에 따라 인물마다 편차가 크다** — 함께 등장하는 인물(왕국 다윗·사울·사무엘·솔로몬, 선지자 엘리야·엘리사, 예수·베드로·야곱 등)엔 잡히고, 어떤 큐레이션 인물과도 공동등장이 없는 고립 인물(사사들·요나·에스더·다니엘 등)은 비어 ②동시대만 남는다. 빈 섹션은 숨기며 — 억지로 만들지 않고 **공백이 곧 그 인물의 고립을 뜻해 정확**하다. 공유 사건 수 내림차순.
- **동시대 인물 (Contemporary)**: 같은 큐레이션 **시대(era)** 에 속한 인물(원시사·족장·출애굽·정복·사사·왕국·선지자·포로·신약 8구간, `backend/app/curated.py`의 `CURATED`/`ERA_ORDER`). era는 모든 큐레이션 인물에 부여돼 있고 각 구간에 2인 이상이라 **항상 1명 이상** 나온다 — 함께 등장한 인물이 비는 인물의 유일한 연결 축이 된다. 함께 등장한 인물에 이미 나온 인물은 중복 제거한다.

→ [[여정-journey]], [[탐색-관점-navigation-perspective]]

## 인물 관계 (Person Relations)

한 인물이 다른 인물과 맺는 관계의 **성격(valence)** 과 그 **시간적 변화**를 손큐레이션으로 담아 **전용 화면**으로 보여주는 축. [[인물-연결-person-connections]]이 그래프에서 파생한 *연결의 존재*(누가 누구와 같은 사건에)만 보여주는 것과 달리, 인물 관계는 그 관계가 **긍정·부정·중립 중 무엇이며 시간에 따라 어떻게 변하는지**를 사람이 붙인 라벨로 표현한다 — valence는 사건 참여로 파생 불가라 반드시 큐레이션이다. **네트워크 그래프가 아니다**(GraphView 삭제 결정 유지) — 시간축 기반 레이아웃으로 표현한다.

- **valence (관계 성격)**: `긍정`·`부정`·`중립` 세 값. 그 시점 관계의 지배적 성향.
- **관계 유형 (type)**: valence와 **직교하는 구조적 분류** — 가족·연인·친구·신하·선지자·스승제자·대적·군주·하나님 등(`스승제자` = 랍비-제자·후계 계승, 엘리↔사무엘·엘리야↔엘리사·예수↔제자; `하나님` = 인물↔하나님의 언약·부르심·순종·반역·심판 축으로, 상대 endpoint는 큐레이션 인물이 아닌 `하나님` 이름 라벨이며 valence로 순종·반역·회개의 변화를 국면에 담는다). valence가 시간에 따라 변하는 감정 성향이라면, 유형은 그 인물이 상대와 맺는 **고정된 관계 종류**다(pair 단위 1개). 뷰에서 유형별 아이콘으로 표시하고 유형끼리 모아 정렬한다.
- **국면 (phase)**: 한 관계 = 시간순 국면 배열. 관계는 성경 서사에서 변한다(다윗↔사울: 총애→시기·추격→살려줌). 각 국면은 valence·라벨·**근거 구절**·대략 연도를 가진다. 변하지 않는 관계는 국면이 하나.
- **레인 (lane) / 초점 쌍 (focus pair)**: 표현의 두 층. **레인** = 관계마다 가로 한 줄, 시간축 위 valence 색 띠(교차선 없이 개요). **초점 쌍** = 한 관계를 골랐을 때 두 인물을 마주 세우고 국면을 시간순으로 잇는 상세.
- **근거 구절 레이어 (evidence verse layer)**: 국면을 누르면 그 관계 근거인 성경 구절 **본문**(한/영)을 레이어로 조회. 근거는 두 층 — **앵커 절**(그 국면의 기준이 되는 한 절)과 **문맥 범위**(앵커를 이해하게 하는 같은 장 안의 주변 절들, 앵커 포함). 문맥 범위가 있으면 범위 절들을 앵커 강조와 함께 보여주고, 없으면 앵커 절 하나로 폴백한다. 구절 본문은 빌드타임 getbible 프리베이크(ADR-0003 선례)로 미리 받아 저장.
- **person-centric (한 인물 기준, 비대칭)**: 주체 인물 하나 기준으로 상대들을 담으며 상대는 **큐레이션 인물이 아니어도 된다**(요나단·밧세바·압살롬 등). 상대가 큐레이션이면 그 여정으로 점프 가능, 아니면 이름 라벨로만 남는다.
- **역할 라벨 (role, 원근 비대칭)**: 가족류 관계에서 각 endpoint는 자기 역할 라벨(`role`)을 가지며 — 아담↔아벨은 아담=`아버지`, 아벨=`둘째 아들` — **뷰는 늘 상대 endpoint의 role을 표시**한다. 그래서 아벨 상세엔 아담이 `아버지`로, 아담 상세엔 아벨이 `둘째 아들`로 원근이 맞게 읽힌다(관계는 pair 하나지만 라벨은 양쪽에서 다르다). 상대가 비큐레이션이면 상대를 가리키는 단일 라벨(`note`)로 대신한다. **role이 화면에 뜨려면 관계의 양쪽 endpoint에 `slug`가 있어야 한다** — 백엔드가 `slug`→`theographic_id`로 키를 만들어 조회하기 때문이다(이름 문자열로 키를 만들면 동명이인에게 다른 서사의 role이 유출된다, task#263). slug 없는 가족 관계에 role을 달면 **조용히 표시되지 않는다**.

→ [[여정-journey]], [[인물-연결-person-connections]], [[화면-단계-stage]]

## 가계도 (Family Tree)

한 인물을 중심으로 **혈통(kinship)** 을 세대별로 세워 보여주는 전용 화면. 데이터는 **그래프 혈통 간선** — 부모↔자식(`PARENT_OF`/`CHILD_OF`), 형제(`SIBLING_OF`), 배우자(`PARTNER_OF`) — 에서 파생하며, theographic 원본의 `father`/`mother`(배열)를 적재하는 것이 원천이다. **혈통 단절의 1차 보충은 가족 폐포 wip 인물의 실레코드 적재**([[publish-레코드]]의 예외, ADR-0021)이고, **원본에 아예 없는 인물만 [[저작-인물-authored-person]] 패턴으로 저작 보충**한다(재저작이 아니라 구멍 메우기). 대표 계보 1건(예수의 족보 — 마태복음 1장)은 이 보충으로 뿌리까지 무단절을 보증한다.

세 이웃 개념과 명확히 구분된다:

- **SidePanel "이웃"의 가족(직계 1-hop)** 과 달리, 가계도는 같은 그래프 간선을 **다세대로 확장**한다 — 위로 조상선을 뿌리까지(단, [[앵커-인물]] 사이 비앵커 구간은 "…N대" **접힌 세그먼트**로 압축, 탭하면 인라인 펼침), 아래로 자손 2세대까지(자식 세대는 [[어머니-그룹]]으로 묶고, 손주는 요약 칩으로 축약), 형제·배우자는 focus 행에 인라인. 노드 탭은 [[인물-미니-카드]]를 열며, **재중심화(ego-centric)** 는 카드 안의 동작이다.
- **[[인물-관계-person-relations]]**(서사 valence·국면)와 달리, 가계도의 **간선**에는 valence·국면·근거구절이 없다 — 구조적 혈통만 담는 결정적 그래프 파생 뷰다. (미니 카드가 보여주는 소개·구절은 관계가 아니라 **인물** 데이터다. person_relations의 "가족" 유형이 방향 role 라벨을 손큐레이션으로 담는 것과 별개 축이다.)
- **삭제된 GraphView(포스-디렉티드 네트워크)** 와 달리, 가계도는 세대가 축을 이루는 **계층 트리**다 — 자유 배치 네트워크가 아니다. 라이브러리 없이 손수 SVG/CSS로 렌더한다.

**앵커 인물 (anchor person)**: 접힌 조상선에서도 항상 노출되는 인물 — 인장 선화(ADR-0025) 보유 인물 + focus의 직계 3세대(부모·조부모). 인장이 곧 "이야기가 있는 인물"이라는 신호로, 앵커 여부와 도상 위계가 일치한다.

**메시아의 실 (messianic thread)**: 아담→예수 계보 경로(마태1+눅3 사슬)에 놓인 간선만 금색으로 강조하는 시각 장치. 접힌 세그먼트가 계보 위면 금 점선. "모든 계보가 예수로 흐른다"는 페이지의 주제의식을 한 줄로 담는다.

**어머니 그룹 (mother group)**: focus 자식 세대의 표시 단위 — 어머니 간선이 있는 자식은 어머니별 컨테이너로 묶고 어머니 이름을 그룹 라벨로 표시, 미상은 무라벨 그룹. 커넥터는 자식 개개인이 아니라 그룹당 1개. 어머니 간선은 성경에 기록된 경우만 저작 보강한다(ADR-0027).

**인물 미니 카드 (person mini card)**: 가계도 노드 탭 시 열리는 바텀시트 요약 — 인장·이름(한/영)·신분 한줄(role)·생몰·시대·소개 일부·언급 구절·부모, 그리고 재중심화/인물 페이지 이동 동작. 인물의 데이터 보유 계층(큐레이션 35 → 소개 보유 → 단역)에 따라 자연 폴백하며, 전원이 최소 신분 한줄은 갖도록 2단 저작으로 커버한다(ADR-0027).

→ [[인물-관계-person-relations]], [[저작-인물-authored-person]], [[화면-단계-stage]]

## 구절 레이어 (Verse Layer)

근거 구절 본문(한/영)을 현재 화면 위에 겹쳐 보여주는 오버레이. [[구절 근거 원칙 (verse-grounded principle)]]의 UI 종착점 — 앱 어디서든 📖 근거 칩·사건·국면을 누르면 같은 패턴의 레이어가 뜬다. 개념상 **앱 전체에 하나의 패턴**이며(소개·여정·연표·관계·의존도·단어 분포·상세 시트 등 진입점만 다르다), [[상세-시트-detail-sheet]]와 구분된다 — 상세 시트는 선택 대상의 상세 *화면*이고, 구절 레이어는 그 위에 잠깐 떠서 본문을 읽히고 닫히는 1회성 조회 층이다. 모바일에서는 화면 아래에서 올라오는 시트로, 데스크톱에서는 중앙 카드로 나타난다. [[인물-관계-person-relations]]의 "근거 구절 레이어"는 이 패턴의 관계판 인스턴스다. 양피지(paper) 질감이 이 레이어의 시각 정체성이다 — 구절 본문은 항상 양피지 위에 놓인다.
_Avoid_: "구절 팝업"·"구절 모달"(구현 형태에 묶인 이름 — 모바일에선 모달이 아니라 시트다)

## 테마 (Theme)

앱 전체 명암 팔레트의 선택 단위. 두 벌 — **Night Atlas(다크, 기본)**: 심야 네이비 표면 + 금 액센트 + 웜 잉크, 앱의 브랜드 무드("어둠 속에서 말씀·땅을 읽는다"). **Day Atlas(라이트, 옵트인)**: 웜 아이보리(양피지 계열) 표면 + 다크 웜 잉크 + 진한 금 — Night Atlas의 명도 반전 대응이지 별개 디자인이 아니다. 사용자가 토글로 명시적으로 전환하며 OS 설정을 자동 추종하지 않는다. 지도와 그 위 오버레이는 테마 불변. (ADR-0013 → ADR-0020 부분 개정) → [[화면-단계-stage]]

## 인물 소개 (Person Context)

큐레이션 인물의 [[화면-단계-stage]] 소개(intro) 탭에 담기는 **정체성 콘텐츠** — 그 인물이 *누구이고 왜 중요한가*를 한눈에 전한다. 세 요소: **역할(role)** 한 줄 별칭("최초의 사람"), **소개문(intro)** 2–3문장, 그 산문을 뒷받침하는 **근거 구절(verses, 대표+근거 겸함)**. 프로젝트 저작 원칙에 따라 **모든 소개·역할은 성경 구절을 근간으로 하며 근거 구절 없는 진술을 두지 않는다** — [[인물-성품-character-trait]]이 성품마다 근거 구절을 다는 것과 같은 결이다. [[인물-관계-person-relations]](관계의 성격·변화)·[[인물-성품-character-trait]](성품)·[[여정-journey]](행적)과 구분되는 축으로, 소개 탭은 이 셋을 정체성으로 묶고 나머지 깊은 탐색(발자취·타임라인·관계)으로 가는 **관문** 역할을 한다. 손큐레이션 오버레이이며 구절 본문은 빌드타임 프리베이크(ADR-0003 선례). → [[인물-성품-character-trait]], [[인물-관계-person-relations]], [[화면-단계-stage]]

## 하나님 상호작용 mode (God-interaction mode)

한 인물의 생애에서 **하나님과의 상호작용 순간** 하나하나를 분류하는 **5종 통제어휘**. `물음-응답`(묻고/기도하고 → 하나님이 응답·이루심), `물음-침묵`(구했으나 → 침묵·거절), `독단-개입`(안 묻고 행했으나 → 하나님이 그래도 붙드심), `독단-어긋남`(안 묻고 행해 → 어그러짐), `부르심`(하나님이 먼저 부르심/명하심/언약하심 — 인물 주도 아님. **명령형**은 인물이 행할 것을 명하거나 따르라 부르심이라 `obeyed` 불리언으로 순종/불순종을 가르고, **언약형**은 창조·언약·택하심/기름부음·예고·신적 선언처럼 인물이 **수령**하는 것이라 `covenant`로 표시해 결과를 '받음'으로 나타냄 — 둘 다 "하나님과 정렬"이라 [[하나님-의존도-god-reliance]] 분자에 든다). [[인물-관계-person-relations]]의 `valence`(관계의 톤: 긍정/중립/부정)와 **다른 축** 이다 — mode는 "누가 주도했고 어떻게 응했나"를 담는다. **`독단`↔`물음` 경계(중요)**: `독단`은 하나님을 배제하거나 거스르는 주제넘은 자기 판단(사울의 자의적 제사·다윗의 인구조사)이고, **믿음의 예배·제사·헌신·의탁은 독단이 아니라 `물음-응답`**(하나님께로 나아감)이다 — 이 경계를 틀리면 아벨(히 11:4)처럼 믿음의 사람이 의존도 0%로 나오는 오류가 난다([[하나님-의존도-god-reliance]] 정의상 물음은 의존, 독단은 반대편). **표시명(중요)**: `물음-응답`은 petition(묻다·기도)만이 아니라 위 경계대로 믿음의 예배·헌신·동행까지 담으므로, UI는 계기 라벨·헤더를 그 상위 개념 **"나아감"**(헤더 `나아감·응답`/`나아감·침묵`, 계기 라벨 `나아감`, kind 뱃지도 petition 어투를 뺀 `그대로 이루심`/`넘치게 이루심`/`그대로는 아니`)으로 표시한다 — **key·데이터·% 는 `물음-응답` 그대로이고 표시만 나아감**이다(에녹처럼 구한 것 없는 인물이 "요청"으로 오표기되지 않게. task 188). 각 항목은 구절 근거를 필수로 가진다([[구절 근거 원칙 (verse-grounded principle)]]). 각 순간은 **계기(trigger)→결과(outcome) 2단**으로 저작되며(각 단 구절 근거 필수, 같은 절이면 UI가 카드 1개로 합침; 명령 위반처럼 인물의 **행동**이 계기·결과와 구분되는 사건은 선택적 중간 단 `response`를 넣어 **3단 계기→행동→결과**로 저작 — 예: 선악과의 부르심→불순종→심판), **물음 계열(`물음-응답`·`물음-침묵`) outcome엔 응답 성격 `kind`** — `이룸`(요청대로)·`더하심`(그 이상)·`다르게`(다른 방식)·`거절`(안 주심)·`침묵`(무응답) — 를 표시축으로 붙인다(**표시 전용, 지표 % 무관**; 부르심/독단은 mode·obeyed에서 UI가 파생). 통제어휘·저작 규칙 정본은 `data/god_reliance/AUTHORING.md`(선례: word_sentiment·character_traits). → [[하나님-의존도-god-reliance]], [[인물-관계-person-relations]]

## 하나님 의존도 (God-reliance)

각 인물이 "얼마나 하나님을 의지했나"를 나타내는 **퍼센트 지표**. 그 인물의 [[하나님 상호작용 mode (God-interaction mode)]] 순간들을 집계해 **(물음-응답 + 물음-침묵 + 순종한 부르심) ÷ (전체 순간) × 100** 으로 계산한다("하나님과 정렬" 정의, ADR-0023). 인물↔인물 상호 관계가 아니라 **인물↔하나님** 한 축의 궤적이며, **구절 근거가 있는 주요 순간들에 대한 큐레이션 해석** 이지 전수 통계가 아니다. **귀속 원칙**: 각 순간은 **그 인물이 직접 당사자인**(하나님이 그를 대면·그가 하나님을 향해 행한) 하나님-상호작용이어야 한다 — 하나님이 **제3자에게** 하신 선언이나 인물 **미출생** 시의 예고는 그의 순간이 아니라 제외한다(예: 창3:15는 뱀에게 하신 원시복음이라 아담에서 제외). **사건 단위 원칙**: 하나의 상호작용 사건은 **하나의 순간**으로만 센다 — 명령·행동·심판·후행 여파는 별도 순간이 아니라 한 순간의 단(step)으로 잇는다(예: 선악과 범죄를 명하심/따먹음/심판대/추방/930세 죽음 5개 순간으로 쪼개면 한 죄가 분모에 5번 계수되는 왜곡). 기록이 희소한 인물(아벨·에녹 등)은 "표본 적음" 뱃지로 신뢰도 한계를 밝힌다. 헤드라인 %(도넛 게이지)·mode 분해 막대·생애 궤적(연도축 mode색 점)·은혜 하이라이트(`독단-개입`)·인물 간 랭킹·성경 평균 대비 백분위로 [[화면-단계-stage]] 탐험 뷰의 전용 내비 탭에 렌더한다. → [[하나님 상호작용 mode (God-interaction mode)]], [[인물-관계-person-relations]]

## 장 묶음 (Chapter Section)

한 권 안의 장들을 이름 붙은 **연속 구간**으로 나눈 대단락. 각 묶음은 짧은 한글 제목과 장 범위(startChapter–endChapter)를 가지며, 한 권의 묶음들은 **연속·전수·비중첩**이다 — 모든 장이 정확히 하나의 묶음에 속하고 1장부터 마지막 장까지 빈틈·겹침이 없다. 장마다 한 줄 요약을 다는 **장 개요**(task#206, 장 단위)와 달리 장 묶음은 **장 위 계층**으로, [[상세 시트 (Detail Sheet)]]의 본문 리더 목차를 평면 목록에서 구조화된 개요로 격상한다(창세기 = 원시 역사 1–11 / 아브라함 12–25 / 이삭·야곱 25–36 / 요셉 37–50 식). 단장권 5권(옵·몬·요이·요삼·유)은 나눌 것이 없어 묶음을 두지 않는다(목차는 평면 폴백). 프레이밍은 보수 스터디 성경의 **문학·서사 개요 구분**을 따르고 문서비평식 자료 구분(자료가설·제2이사야 등)은 쓰지 않는다([[Book]] 보수 연대·ADR-0014와 일관). 추정·저작 독립 데이터라 Neo4j 주입이 아니라 오버레이(`data/chapter_sections/books.json`, bookId 키 — chapter_summaries 선례·ADR-0004)로 서빙한다. → [[Book]], [[구절 근거 원칙 (verse-grounded principle)]]

## 메시아 예언→성취 (Messianic prophecy → fulfillment)

구약의 메시아 예언절과 신약의 성취절을 짝지은 큐레이션 쌍으로, 탄생·사역·수난·부활 등 주제로 묶인다. **직접 인용과 구분**: 앱의 구약↔신약 인용(`data/quotations/quotations.json`)이 신약이 구약을 *문자적으로 인용*한 쌍인 데 반해, 메시아 예언→성취는 인용이 아닌 **주제적 성취**(예: 시22편 손발 찔림 → 십자가)도 포함한다 — 즉 메시아 성격 인용(부분집합)에 비인용 성취를 더한 상위 묶음이다(기존 quotations 항목에 이미 "처녀 잉태 임마누엘 예언" 등이 섞여 있어 태깅으로 도출). 각 쌍은 [[구절 레이어 (Verse Layer)]]로 양쪽 절 본문을 보여준다. → [[구절 레이어 (Verse Layer)]]

## 언약 (Covenant)

하나님이 특정 인물·백성과 맺으신 주요 언약(노아·아브라함·모세·다윗·새 언약 등). 당사자·약속·표징·핵심절·시대를 갖고 [[사건 연대 (startDate)]] 규약으로 연표에 배치돼 구속사 전체를 가로지르는 주제 실이 된다. [[하나님 상호작용 mode (God-interaction mode)]]의 `부르심` 언약형(인물이 수령하는 신적 선언)과 결이 같으나, 언약은 *인물별 순간*이 아니라 **서사 전체를 잇는 독립 축**으로 저작한다. → [[사건 연대 (startDate)]]

## 비유 (Parable)

예수가 가르치신 비유. 위치·구절이 붙은 [[저작 사건 (Authored Event)]]으로 저작해 지도·연표에 색인 레이어로 얹으며, 종류 태그로 [[기적 (Miracle)]]과 구분한다. → [[기적 (Miracle)]], [[저작 사건 (Authored Event)]]

## 기적 (Miracle)

예수 사역 중의 기적. [[비유 (Parable)]]와 동일하게 위치·구절이 붙은 [[저작 사건 (Authored Event)]]으로 저작해 색인 레이어로 얹으며 종류 태그로 비유와 구분한다. → [[비유 (Parable)]]

## 주제 성구 (Topical Verse Collection)

믿음·사랑·용서·기도 등 **주제(topic)**별로 큐레이션한 성구 묶음. 주제 선택 시 [[구절 레이어 (Verse Layer)]] 패턴으로 성구 본문을 렌더한다. **[[테마 (Theme)]]와 다른 개념** — 테마는 명암 팔레트(Night/Day Atlas) 선택 단위이고, 여기의 "주제"는 성경 내용의 화제 분류다(용어 충돌 주의).

**주제 간 구절 재사용은 허용된다.** 한 구절이 둘 이상의 주제에 정당하게 속할 수 있으므로 `verseId`는 주제마다 독립이고 중복 금지 규칙이 없다 — 엡2:8(49002008)은 `faith`와 `salvation` 양쪽에 들어 있고 내용상 둘 다 옳다(2026-07-24 저작 실측). 즉 이 묶음은 **분할(partition)이 아니라 덮개(cover)** 다. 주제별 성구 수를 합해 전체 성구 수로 읽으면 안 된다.

→ [[구절 레이어 (Verse Layer)]]


## 통합 검색 (Unified Search)

이름과 구절 본문을 한 입력창에서 함께 찾는 검색. 결과는 두 부류다 — 그래프 노드(인물·장소·사건)의 **이름 일치**, 그리고 성경 본문의 **문자열 일치**. 구절 결과는 그 절이 있는 장 본문으로 이어지므로, 찾은 절을 문맥 안에서 읽는 흐름이 된다.
_Avoid_: "단어 검색"([[단어 분포]] 화면의 명사 색인과 혼동된다 — 통합 검색은 활용형을 포함한 본문 문자열 일치다)

## 단어 분포 (Word Distribution)

한 권(또는 전체) 안에서 명사가 얼마나 자주 나오는지의 분포. 빌드타임에 형태소 분석으로 뽑은 **명사 색인**이 출처이므로, 조사·활용형을 포함하는 [[통합 검색 (Unified Search)]]과 매칭 방식이 다르다. 같은 낱말을 물어도 두 화면의 결과 수가 다를 수 있고, 그것은 결함이 아니다.

## 북마크 (Bookmark)

사용자가 명시적으로 저장한 화면. 저장 단위는 인물·구절·장·투어 등 [[화면 단계 (Stage)]] 하나이며, 해시 문자열로 표현되어 복원은 딥링크와 같은 경로를 탄다. 이 기기에만 남는다.
_Avoid_: "즐겨찾기"(브라우저 기능과 혼동)

## 이어보기 (Recent)

사용자가 저장하지 않아도 자동으로 기록되는 최근 방문 화면. [[북마크 (Bookmark)]]와 저장 방식·복원 경로는 같지만 **의도의 유무**가 다르다 — 북마크는 "남기겠다"는 선택이고 이어보기는 자취다. 따라서 이어보기는 상한을 두고 오래된 것부터 밀려난다.

## 이어읽기 (Resume Reading)

마지막으로 읽은 책에서 **아직 읽지 않은 가장 앞 장**. [[읽기 진도 (Reading Progress)]]의 읽은 장 집합과 마지막 위치에서 파생되는 한 점이며, 저장되는 값이 아니라 매번 계산되는 값이다.

**그 책을 완독했으면 이어읽기는 없다.** 완독을 판정하려면 그 책의 총 장 수가 필요하므로, 이어읽기를 그리는 화면은 장 수를 **그 화면이 실제로 부르는 응답으로** 함께 받아야 한다. 장 수를 모르는 동안에는 이어읽기를 내보내지 않는다 — 없는 장을 가리키는 버튼을 잠깐 보여주고 고치는 것보다 늦게 나타나는 편이 낫다. 같은 상한 검사가 이미 오염된 저장값(총 장 수를 넘는 장이 들어간 기록)도 함께 걸러낸다.

[[이어보기 (Recent)]]와 한 글자 차이지만 다른 것이다 — 이어보기는 **방문한 화면**의 자취이고, 이어읽기는 **읽지 않은 장**을 가리키는 진도 파생값이다. 두 이름을 섞어 쓰면 화면 문구와 코드가 서로 다른 것을 뜻하게 된다.
_Avoid_: "이어보기"와 혼용 / "다음 장"(완독 시 존재하지 않는다는 성질이 사라진다)

## 읽기 진도 (Reading Progress)

장 단위로 "읽었다"고 표시한 기록과 그로부터 계산되는 책별·전체 진도율.
_Avoid_: "통독 플랜"(날짜별 목표·일정을 뜻한다 — 진도는 사용자가 지나온 자취일 뿐 정해진 일정이 아니다)

## 장소 페이지 (Place Page)

한 장소를 주어로 삼아 그곳의 배경·핵심 구절·거쳐 간 인물·일어난 사건을 모으는 화면. 인물을 따라가다 장소를 만나는 [[여정 (Journey)]]과 **관점이 반대**다. 어떤 사건이 "그곳에서 일어났는지"의 판정 기준은 여정의 정차 판정과 동일해야 한다 — 두 화면이 같은 장소에 대해 다른 개수를 말하면 안 된다.

## 통사 연표 (Canon Timeline)

특정 인물이나 투어에 종속되지 않고 창세기~계시록 전체를 하나의 축에 놓는 연표. [[Period]]의 시대가 축의 눈금이고 그 위에 사건과 인물의 활동 구간이 겹친다.

**축의 좌표는 연도가 아니라 시대다.** 시대끼리는 실제 시간 길이와 무관하게 대등한 지분을 갖고, **연도 비례는 한 시대 안에서만** 성립한다 — 신약 100년이 전체 4098년의 2.4%인데 사건의 33%를 담고 있어, 전역 연도 비례로는 읽을 수 있는 화면이 나오지 않는다. 시대 간 시간 길이는 각 시대의 연도 범위 표기로만 전달한다.
_Avoid_: 그냥 "연표"(기존의 인물 연표·투어 연표와 구별되지 않는다) / "연도 축"(전역 연도 비례를 뜻하는 것으로 오해된다 — 시대 축이다)

# Coding principles

You are a lazy senior developer. Lazy means efficient, not careless. The best code is the code never written.

Before writing any code, stop at the first rung that holds:

1. Does this need to be built at all? (YAGNI)
2. Does the standard library already do this? Use it.
3. Does a native platform feature cover it? Use it.
4. Does an already-installed dependency solve it? Use it.
5. Can this be one line? Make it one line.
6. Only then: write the minimum code that works.

Rules:

- No abstractions that weren't explicitly requested.
- No new dependency if it can be avoided.
- No boilerplate nobody asked for.
- Deletion over addition. Boring over clever. Fewest files possible.
- Question complex requests: "Do you actually need X, or does Y cover it?"
- Pick the edge-case-correct option when two stdlib approaches are the same size.
- Mark intentional simplifications with a `ponytail:` comment naming the ceiling and upgrade path.

Not lazy about: input validation at trust boundaries, error handling that prevents data loss, security, accessibility, anything explicitly requested.
