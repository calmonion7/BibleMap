# 알려진 리스크 및 우려 사항

## 1. 라이선스 리스크 (위험도: 높음)

- Theographic 데이터는 **CC-BY-SA-4.0** 라이선스다.
- **SA(ShareAlike) 조항**: 이 데이터를 가공·확장한 데이터셋은 동일 라이선스(CC-BY-SA-4.0)로 공개해야 할 수 있다.
- 가공된 Neo4j DB를 독점 자산으로 운용할 계획이라면, **데이터 작업 시작 전에 법률 검토가 필수**다.
- **BY(Attribution) 조항**: 앱 내 크레딧 페이지에 Theographic 출처 표기가 반드시 포함되어야 한다.
- 결정이 미뤄질 경우 Phase 0(Neo4j 적재) 완료 후 되돌리기 어렵다.

## 2. 보안: Neo4j 포트 외부 노출 금지

- Neo4j 포트 **7474(HTTP Browser)** 와 **7687(Bolt)** 는 퍼블릭에 절대 노출해서는 안 된다.
- `docker-compose.yml`에서 호스트 바인딩을 반드시 `127.0.0.1:7474:7474` 형태로 제한해야 한다.
- Cloudflare Tunnel의 ingress 규칙에는 **FastAPI 앱 포트(8000)만** 등록한다. Neo4j 포트는 ingress에 포함하지 않는다.
- FastAPI → Neo4j 연결은 compose 내부 서비스명(`bolt://neo4j:7687`)을 사용하며, 호스트를 경유하지 않는다.
- PortfoliOn은 상태 보유 DB가 없었으므로 이 위험이 신규로 추가되는 항목이다.

## 3. 규모: 인물 3,000+ 동시 렌더링 금지

- 설계 원칙 2에서 인물 3,000명 동시 화면 표시를 **명시적으로 금지**하고 있다.
- **Focus+Context 패턴** 구현이 필수다: 선택된 노드와 1~2촌 이웃 노드만 표시하고 나머지는 숨김 처리.
- 페이지네이션/필터링 구현을 초기 Phase에서 빠뜨리면, 관계도 뷰가 털뭉치(hairball) UX가 되어 후속 Phase에서 대규모 리팩토링이 필요해진다.
- Phase 4(관계도 뷰) 검증 기준은 "인물 선택 시 1~2촌만 표시, 털뭉치 없음"이므로 이 기준을 Phase 1 설계 시점부터 고려해야 한다.

## 4. 한글 이름 커버리지 불완전

- 출시 시점에 **Tier 1**(핵심 인물·지명 수백 개)만 수동 큐레이션된다.
- 나머지 약 2,700+ 인물은 영문명 표시 + `nameKoMissing: true` 플래그로 처리된다.
- Tier 2(위키데이터 기반 자동화)는 아직 설계되지 않은 계획 단계다.
- UI에서 미번역 노드를 명확히 구분하는 처리가 없으면 사용자 경험이 저하된다.
- 개역개정/새번역 등 역본별 인명·지명 표기 차이로 인해, **기준 역본을 1개로 먼저 고정**해야 혼선이 없다(현재 기준: 개역개정).

## 5. 성경 연대 논쟁

- 성경 사건 연대는 학술 전통마다 상이하다(특히 출애굽 시기).
- 단일 타임라인을 정답처럼 제시해서는 안 된다.
- 데이터 출처와 채택된 학술 전통을 UI에서 명시해야 한다.
- Phase 3(타임라인 뷰) 구현 전에 "어떤 연대 체계를 기본값으로 쓸 것인가"를 결정해야 한다.

## 6. 성경 번역 본문 저작권

- 성경 **데이터**(인물·지명·사건 메타데이터)는 자유롭게 사용 가능하다.
- 특정 **번역본 텍스트**(구절 원문 표시)는 저작권 대상이다.
- 구절 본문을 UI에 표시하려면 퍼블릭 도메인 역본을 사용하거나, 해당 번역 단체로부터 라이선스를 확보해야 한다.
- 설계 문서 3.3절에서 구절 본문 텍스트를 한글 매핑 레이어에 **포함하지 않기로** 명시한 이유이기도 하다.

## 7. Docker Desktop 의존성 (취약한 상시 가동 구조)

- 백엔드와 DB가 **Mac 로컬 노트북** 위에서 Docker로 구동된다.
- 재부팅 후 자동 복구를 위해 Docker Desktop의 "로그인 시 자동 시작" 설정이 활성화되어 있어야 한다.
- 노트북 뚜껑을 닫은 채 운용하려면 `sudo pmset -c disablesleep 1` 명령으로 클램셸 잠자기를 차단해야 한다.
- 이 설정들이 누락되거나 변경될 경우 서비스가 조용히 다운된다.
- 하드웨어 장애, macOS 업데이트, Docker Desktop 업데이트 시 수동 개입이 필요하다.

## 8. 테스트 및 CI 인프라 부재

- 현재 코드 없음, 테스트 없음, CI 파이프라인 없음인 사전 구현 단계다.
- 일정 압박 하에서 Phase별 검증 게이트를 건너뛸 위험이 있다.
- 설계 문서의 각 Phase 검증 기준("verify:" 항목)은 다음 Phase로 넘어가기 전 반드시 통과해야 한다.
- Phase 0 완료 후 최소한 Cypher 쿼리 단위의 통합 테스트라도 추가하는 것이 권장된다.
