# 2026-08-19 — 통합 검색: 이름 + 구절 전문 검색 되살리기 (task#267)

## 계획 대비 실제
- 계획대로 된 것: 슬라이스 3개(공용 헬퍼 → `/search` 확장 → 헤더 오버레이 → 결과 클릭 배선) 전부 완료 기준 충족. `words.py`를 같은 헬퍼로 재배선한 뒤에도 기존 응답이 **바이트 동일**(total 518·200건)임을 전후 비교로 확인.
- 이탈:
  - 실행 방식은 Dynamic Workflow가 아니라 **메인 세션 직접 순차** — S1→S2→S3가 전부 직렬 의존이고 S2·S3가 같은 호출부(`App.jsx`)를 건드려 병렬 이득이 0. 회고 `2026-07-14-word-distribution-page`가 정본화한 "공유 파일 직렬 프론트 = 직접 순차" 패턴을 그대로 적용.
  - 절 검색 최소 길이(2자)는 **절 검색에만** 적용하고 노드 이름 검색은 1자에서도 동작시켰다(전수 스캔 방어가 목적이므로).
  - ESLint `react-hooks/set-state-in-effect`에 걸려 프로젝트 관용구(`Promise.resolve().then()` 지연 + `alive` 가드)로 우회.

## 배움
- 다음에 다르게 할 것:
  - **화면 체크의 질의는 데이터로 먼저 확인하고 고정하라.** fg-loop 정지조건 C2를 "'사랑' 입력 시 이름·구절 두 섹션이 모두 1건 이상"으로 못박았는데, `/search?q=사랑`의 `nodes`는 **정당하게 0건**이었다(사랑이라는 이름의 노드가 없다). 계획의 완료 정의가 든 예시 문구("사랑을 입력하면 이름 결과와 구절 결과가 함께 나온다")를 기계 단언으로 그대로 옮긴 것이 원인 — 예시는 사람이 읽는 서술이지 도달 가능한 단언이 아니다. 두 섹션 검증은 `다윗`(nodes 20/verses 20), 구절 경로는 `사랑`(verses 20)으로 나눠 의도를 지키면서 도달 가능하게 고쳤다. **UI 체크를 쓸 때는 그 질의의 API 응답을 먼저 실측할 것.**
  - **응답 형태를 바꿀 때는 소비자 0건임을 먼저 증명하라.** `/search`를 배열 → `{nodes, verses}`로 바꾸기 전에 프론트 호출부가 실제로 0건임을 grep으로 확인했고, 이 한 줄 확인이 "깨질까?"라는 논의를 통째로 없앴다. 기존 응답을 함께 쓰는 `words.py`는 전후 JSON을 파일로 떠서 `==` 비교했다 — 눈으로 훑는 것보다 싸고 확실하다.
