## Learnings
- Do differently next time:
  - **관계 저작 워크플로는 "기존을 베이스로, 제안은 덧붙이기만"이 필수.** 에이전트가 인물별로 제안하면 pair를 상대편에 위임해 일부만 제안한다(david 2/24). 워크플로 산출을 wholesale로 쓰면 대량 손실. 단일 세션 writer가 기존 relations.json을 base로 두고 verse 기준 union(매칭 verse는 검증값 우선), 손실 0을 git 대비로 검증.
  - **워크플로 프롬프트 RULES에는 AUTHORING 규칙 전문을 넣어라 — 특히 규칙 7(집단 제외).** 요약하면 빠뜨린 규칙만큼 오제안이 나오고 사후 정리 비용이 든다.
  - **Workflow args를 신뢰하지 말고 스크립트 상수화.** `args.persons` 배열이 그대로 안 들어와 즉시 실패 — 목록·경로는 스크립트에 직접 박는 편이 안전.
  - **읽기전용 병렬 리서치 + 국면별 적대적 검증 + 단일 writer** 조합은 정확도-우선 대량 저작에 효과적(회귀 없이 실제 오류를 다수 포착). "단일 파일 순차" 제약(병렬 쓰기 금지)과 양립.
  - **백엔드 코드 변경은 `docker compose up -d --build api`** — `restart`는 옛 이미지 코드를 그대로 실행(데이터만 마운트). 후속 quick 작업에서 note→role 백엔드 변경이 restart로 반영 안 돼 재확인. (메모리 project_local_verify_build와 일치.)
- 사소/일회성: context는 반드시 범위(`장:절-절`, 같은 장) — 단일절이면 프리베이크 폴백. 신약 교차참조(히 11:4)도 getbible 프리베이크가 처리(null:0).
