# 2026-07-24 — 인트로 필름에 "컨텐츠 소개" 비트 추가 (task#245)

## Plan vs actual
- What went as planned: 몽타주와 도착지 사이에 컨텐츠 소개 비트를 넣고, 오토플레이·무의존(ADR-0024)·계약 무변경(온오프·딥링크·ⓘ·reduced-motion·도착지 3진입점)이라는 골격/Non-goal은 처음부터 끝까지 지켜졌다. 최종 검증 Playwright 11/11, build·lint 무경고.
- Divergences: **연출(표현)이 사용자 피드백 6라운드를 거치며 크게 전회**했다.
  1. 추상 금색 선 1개 모핑 → "너무 간략, 실제 화면 구성 참고"
  2. 실제 4뷰 딥링크 캡처 → 스켈레톤 미니 목업 → "창 표시 별로, 기계적, 컨텐츠만, A→B 변형"
  3. 창 크롬 제거·페이싱 2.4초·비트 크로스디졸브 → 겹침 도입
  4. 노드 그래프 rAF 모핑 → "장면 겹치는 게 이상함"
  5. 비트 전환을 순차 디졸브(겹침 제거, 측정 peak 0.00)로 교체
  6. 실제 메뉴 스크린샷 3장 + "메뉴 기준·인지·두괄식·자연스러운 전환" → **메뉴 기준 두괄식 장면**으로 재작성, 이후 각 장면에 그려지는 설명 선화(SceneArt) 추가, 인물 헤드라인 "한 사람"→"성경 인물"로 교정.
  구조도 커졌다: 컨텐츠 1비트(내부 순환) → 메뉴 장면 3비트(인물·성경책·투어), `BEAT_MS` 6항목·`END` 6.

## Learnings
- Do differently next time:
  - **주관적 "인트로/온보딩 애니메이션" 요구는 해석 공간이 매우 넓고, 매 라운드 전면 재구현 비용이 크다. 착수 전 방향을 값싸게 먼저 확정하라** — 텍스트/간단 목업으로 (a) 추상 vs 메뉴-기반, (b) 프레임 vs 무프레임, (c) 모핑 vs 개별 장면 3갈래만 A/B로 물었어도 6번 풀 빌드를 ~2번으로 줄였을 것. (메모리 feedback_no_confirm과 상충하지 않음 — 이건 "실행 확인"이 아니라 "디자인 방향"이라 값싼 선확인이 정당.)
  - **"어떤 컨텐츠가 있는지" 알리는 인트로가 실제로 통한 조합(다음 인트로 작업 재사용)**: ① 실제 메뉴/IA에 근거 — 앱의 실제 상단 메뉴명 + `App.jsx`와 동일한 lucide 아이콘·라벨을 그대로 써야 "인지"된다. ② 두괄식 — "무슨 정보를 얻는지"(가치)를 헤드라인으로 먼저, 메뉴 항목은 그 뒤. ③ 창/카드/프레임 크롬은 거부감 — 콘텐츠만. ④ 일러스트는 **앱 자체의 선화 관용구(thread-draw/symbol-draw)**로 — 회색 스켈레톤 와이어프레임은 "기계적", 실제 스크린샷/목업은 "창 같다"로 둘 다 반려됨. ⑤ 시각적으로 다른 장면끼리 **크로스페이드 겹침 = 이중노출로 이상함** → 순차(페이드아웃→페이드인, 동시노출 0) 전환이 "자연스러움"이었다.
  - 기술: 임의 형상 모핑에 CSS `d`/SMIL는 피하고 rAF 좌표 트윈이 됐지만 최종엔 폐기. 인트로가 "진짜 메뉴"로 읽히게 한 결정타는 **앱 내비의 lucide 아이콘 컴포넌트를 그대로 import**한 것.
