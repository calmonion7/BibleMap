# 개인화 데이터(북마크·읽기 진도)는 localStorage 전용으로 두고 서버 쓰기 경로를 열지 않는다

북마크·이어보기·읽기 진도 같은 사용자별 상태를 도입하면서 저장 위치를 정해야 했다. **브라우저 localStorage 전용**으로 두고, 백엔드에는 어떤 쓰기 엔드포인트도 만들지 않는다.

BibleMap은 지금까지 **쓰기 경로가 없는 읽기 전용 파이프라인**이다 — 모든 API 라우트가 `@router.get`이고 CORS도 `allow_methods=["GET"]`이며, 그래프를 채우는 일은 전부 빌드타임 스크립트가 한다. 서버 저장을 택하면 계정·인증·개인정보 보관·백업·GDPR성 삭제 요구가 한꺼번에 따라 들어오고, 단일 self-hosted 스택에 상태 있는 사용자 데이터가 처음으로 생긴다. 얻는 것은 기기 간 동기화 하나뿐인데, 이 앱의 사용 형태(개인이 한 기기에서 읽고 탐험)에서 그 가치가 위 비용을 넘지 않는다. 테마·인트로 숨김이 이미 같은 방식으로 localStorage에 있으므로 관행도 일관된다.

## Consequences

- 기기를 바꾸거나 브라우저 데이터를 지우면 북마크·진도가 사라진다. 이를 손실이 아닌 **설계된 한계**로 보고, 화면에서 "이 기기에 저장됨"임을 드러낸다.
- 저장 키는 `biblemap-` 접두사를 쓰고 각 스키마에 버전 필드를 둔다. 스키마를 바꿀 때 마이그레이션 코드를 쓰지 않고 **파손·구버전은 빈 값으로 폴백**한다(개인화는 유실돼도 앱이 망가지지 않는 데이터다).
- 나중에 계정을 도입한다면 이 결정을 뒤집는 것이 아니라 localStorage를 캐시로 두고 동기화를 얹는 방향이 된다 — 지금 서버 스키마를 미리 만들지 않는다.
- CORS의 GET 전용 설정과 "쓰기 경로 없음"이라는 아키텍처 서술은 이 기능 도입 후에도 여전히 참이다.
