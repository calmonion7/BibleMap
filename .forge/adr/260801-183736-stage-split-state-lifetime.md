# 스테이지를 파일로 분리할 때 상태의 수명은 언마운트 경계로 결정한다 — 코드는 훅, 수명은 생존 조상

## Status

Accepted (2026-08-01) — task#258(App.jsx 분해 2부)에서 도출·검증. CONTEXT.md 「화면 단계」의 "유지해야 하는 상태는 컴포넌트 state로 못 지킨다" 규약에 **분해 상황용 분기**를 추가한다.

## Context

App.jsx가 각 화면 단계를 `{activeStage === 'x' && …}`로 조건부 렌더하므로 **단계 이탈 = 언마운트**다(CONTEXT.md 「화면 단계」). App.jsx가 1081줄까지 자라 분해(task#257~258)에 들어갔고, 탐험 스테이지를 `ExploreStage.jsx`로 빼면서 그 스테이지만 쓰는 여정 데이터 상태(정차지 목록·선택 정차지·투어 메타·인물 사건 목록)를 함께 옮기는 것이 응집상 자연스러워 보였다.

그런데 탐험 6탭 중 **'족보'는 탭 전환(`setExploreView`)이 아니라 전용 스테이지 진입(`openFamily`)**이다. `useStageNavigation`의 `handleOpenFamily`는 `activeStage`를 `'family'`로 바꾸면서 `explorePersonId`는 **유지**하므로, 사용자 입장에선 "탐험 안의 탭"인데 실제로는 **explore 블록 전체가 언마운트**된다. 상태를 `ExploreStage`가 소유하면 언마운트와 함께 소실돼, 족보에서 돌아올 때 **여정 재fetch + 선택 정차지 초기화**라는 회귀가 생긴다. 족보는 실사용 빈도가 높은 탭이라 사용자에게 그대로 드러난다.

이 함정은 **코드를 읽어서는 안 보인다** — `ExploreStage`만 보면 여정 상태는 이 컴포넌트 전용이고, 부모가 소유할 이유가 없어 보인다. 그래서 다음 사람이 "이 훅은 ExploreStage 전용인데 왜 App에서 부르지?"라며 옮기고 조용히 회귀시키기 쉽다.

## Decision

- **스테이지를 별 파일 컴포넌트로 분리할 때, 그 스테이지를 벗어나도 유지돼야 하는 상태는 분리된 컴포넌트가 소유하지 않는다.** 소유자는 언마운트를 견디는 **생존 조상**(현재 구조에선 App) 또는 모듈 스코프 메모리다.
- **대신 코드만 훅(`use*.js`)으로 뺀다** — 본문 얇게 만들기와 상태 수명 유지를 동시에 얻는다. 훅은 생존 조상이 호출하고, 반환을 **단일 객체 prop**으로 분리 컴포넌트에 내린다(한 훅이 만든 응집된 단위를 개별 prop으로 흩지 않는다).
- **훅 상단에 "왜 여기서 호출해야 하는가"를 구체적인 언마운트 경로와 함께 주석으로 고정한다.** "옮기지 말 것"까지 적는다. 이 주석이 없으면 위 Context의 오해가 그대로 재발한다.
- **분해 태스크의 검증에 언마운트 왕복 회귀 가드를 필수 슬라이스로 넣는다** — 해당 스테이지를 떠나 다른 스테이지로 갔다 돌아올 때 ① 데이터 재fetch 0건(네트워크 캡처로 확인) ② 사용자 선택 상태 유지. 화면 스크린샷·계산 스타일 검증으로는 절대 잡히지 않는 축이다.
- 판정 기준은 하나다: **"이 상태는 언마운트 경계를 넘나드는가?"** 넘지 않으면(그 스테이지 안에서만 살면 되는 파생값·재생 시퀀서 등) 분리 컴포넌트가 소유해도 무해하다.

## Considered Options

- **상태를 분리 컴포넌트로 함께 이관** — 응집은 최선이지만 위 회귀가 발생한다. 기각.
- **Context 도입** — 수명 문제를 우아하게 풀지만 CONVENTIONS §5.4가 "전역 상태 라이브러리 없음(Redux/Zustand/Context 미사용), 공유 값은 App이 소유하고 props로 내려준다"를 명시하고 실제 `createContext` 사용이 0건이다. 관례 이탈 비용이 이득보다 크다. 기각.
- **모듈 스코프 메모리**(`scrollMemory.js` 패턴) — 세션 내내 유지되는 스크롤 위치엔 맞지만, 여정 데이터는 인물/투어가 바뀌면 무효화돼야 해서 리액티브 소유가 맞다. 기각(이 패턴은 "리마운트를 견뎌야 하는 비-리액티브 값"용으로 남는다).

## Consequences

- **분리 컴포넌트의 prop 수가 늘어난다.** `ExploreStage`는 20개(여정 객체 1 + 내비 상태 13 + 선택 3 + 전역 3). 응집 대신 명시성을 택한 대가다. 지금은 감당 가능하지만 다음 분해에서 더 늘면 CONVENTIONS §5.4 재검토가 안건이 된다.
- **다음 분해(`SidePanel.jsx` 928줄 등)마다 이 판정이 선행돼야 한다** — 옮길 상태 목록을 놓고 "언마운트 경계를 넘나?"를 먼저 답한다.
- 검증 비용이 늘어난다(왕복 가드 시나리오 추가). task#258에서는 이 가드가 데스크톱·모바일 양쪽에서 `journey` 재요청 0건 + 정차지 유지를 확인해 설계가 실제로 작동함을 입증했다.
- 이 결정은 **App.jsx가 유일한 생존 조상**이라는 현 구조에 의존한다. 라우터 도입 등으로 스테이지 렌더 방식이 조건부 렌더에서 벗어나면 전제부터 재검토해야 한다.
