# 배포 검증 게이트는 fail-closed — 스킵은 배포 경로에서 실패로 승격하고, 데이터 주입은 게이트보다 앞선다

`scripts/check.sh`는 환경 미충족 항목(ESLint의 `frontend/node_modules`, 연대 검증의 Neo4j)을 `⊘` 한 줄만 찍고 통과시켜 왔고, `deploy.sh`가 `npm install`보다 **먼저** 게이트를 부르는 순서 버그 때문에 클린 체크아웃의 첫 배포에서는 ESLint가 항상 스킵된 채 `check PASS`가 찍혔다. 순서만 바로잡는 대신 **`CHECK_STRICT=1`일 때 두 스킵 분기가 실패가 되도록 게이트 안에 보증을 내리고**, `deploy.sh`가 이 변수를 켜고 호출하기로 한다 — 고치려는 결함의 정체가 "호출 순서 때문에 게이트가 조용히 스킵됐다"이므로, 순서로만 고치면 같은 결함 클래스(누군가 다시 재배치하면 또 무음 통과)가 그대로 열려 있기 때문이다. 스킵-경고 계약 자체는 남긴다: Neo4j 없이 파일 검증 12종만 돌리는 단독 개발 실행은 여전히 정당한 용법이고, 엄격 모드는 배포 호출자만 켠다.

함께, `inject_ko_names.py`·`inject_date_corrections.py`를 **게이트보다 앞**으로 옮긴다. 뒤에 두면 아무 일도 하지 않기 때문이다 — 교정이 롤백된 DB 상태에서는 게이트의 `validate_event_chronology`가 먼저 배포를 중단시켜 주입 단계에 도달하지 못하고, 게이트가 통과하는 경우엔 이미 교정이 적용돼 있어 주입이 no-op이다. 주입은 멱등이므로 검증 전에 실행해 DB를 정본 상태로 되돌린 뒤 게이트가 판정하게 하는 것이 맞다.

반면 **`load_*` 로더는 배포에 배선하지 않는다.** `load_books.py`의 `build_book_year_range()`가 업스트림(Ussher) 이벤트에서 `startYear`/`endYear`를 재산출하므로, 로더를 자동화하면 교정을 지키는 게 아니라 매 배포마다 깨뜨리게 된다. 그래프 적재는 저작 시점 수동으로 남긴다(ADR-0014의 재실행 조항과 함께 읽을 것).

## Consequences

- Neo4j가 죽어 있으면 배포가 게이트에서 막힌다. 새 제약은 아니다 — 기존에도 주입 단계의 15회 재시도 실패로 배포가 중단됐고, 이제 그 실패가 프론트·이미지 빌드 **앞**으로 당겨져 시간을 아낀다.
- 라이브 DB 드리프트가 코드와 무관한 프론트 배포까지 막는 결합(의도된 fail-closed)은 이 결정의 범위 밖이다. 완화하려면 "어떤 실패는 배포를 막지 않는가"라는 별개 정책이 필요하다.
